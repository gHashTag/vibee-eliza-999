## 📖 ТИПЫ ПАМЯТИ (Психология → AI)

**В психологии (человек):**

1. **Сенсорная память** — миллисекунды (вспышка света)
2. **Short-Term Memory (STM)** — секунды/минуты (телефонный номер)
3. **Long-Term Memory (LTM)** — годы/вся жизнь (детские воспоминания)

**В AI-агентах:**

1. **Контекст (Context Window)** = STM (4K-1M tokens)
2. **Vector Database** = LTM (бесконечно, пока есть место)
3. **Parameters (веса модели)** = "Врожденные" знания

## 1️⃣ SHORT-TERM MEMORY (Контекстное окно)

### 📖 ОПРЕДЕЛЕНИЕ

**Short-Term Memory (STM)** — это память в пределах **контекстного окна** (context window) модели.

**Формула:**

```
Context Window = Количество tokens, которые модель "видит" одновременно
```

**Размеры (2024):**

```
GPT-3.5: 4K tokens (~3,000 слов)
GPT-4: 8K/32K/128K tokens
Claude 3: 200K tokens (~150,000 слов)
Gemini 1.5: 1M tokens (~750,000 слов)
```

---

### 🧠 КАК РАБОТАЕТ

**Пример (GPT-4, 8K tokens):**

```
┌──────────────────────────────┐
│  Context Window (8K tokens)  │
│                              │
│  System Prompt:   500 tokens │
│  User Message 1:  200 tokens │
│  AI Response 1:   300 tokens │
│  User Message 2:  150 tokens │
│  AI Response 2:   250 tokens │
│  ...                         │
│  User Message N:  100 tokens │
│  [Генерация ответа...]       │
│                              │
│  ИТОГО: 7,500 / 8,000 tokens │
└──────────────────────────────┘

Следующее сообщение:
User: "..." (200 tokens)
→ 7,500 + 200 = 7,700 tokens OK

Еще одно:
User: "..." (500 tokens)
→ 7,700 + 500 = 8,200 tokens ❌ ПЕРЕПОЛНЕНИЕ!

Решение:
→ Удалить старые сообщения (User Message 1 + AI Response 1)
→ Освободить 500 tokens
```

---

### 💡 ПРОБЛЕМЫ

**Проблема 1: Забывание**

```
Диалог на 100 сообщений
Контекст: 8K tokens
→ Модель "забывает" первые 70 сообщений

User: "Помнишь, что я говорил в начале разговора?"
ChatGPT: "Извините, не помню"
```

**Проблема 2: Стоимость**

```
Gemini 1.5: 1M tokens контекста
Стоимость: $0.001 / 1K tokens
→ $1 за ОДНО сообщение с полным контекстом

100 сообщений в день = $100/день = $3,000/месяц
→ Дорого!
```

### ✅ РЕШЕНИЯ

#### 1. Сжатие контекста (Summarization)

**Идея:** Старые сообщения → краткое резюме

**Пример:**

```
Было (20 сообщений, 7K tokens):
User: "Расскажи про Python"
AI: [300 tokens об истории Python]
User: "Какие есть фреймворки?"
AI: [400 tokens про Django, Flask...]
...

Сжато (резюме, 500 tokens):
"Обсуждали: Python (история, синтаксис), фреймворки (Django, Flask)"

Сохранено: 6,500 tokens → Теперь можем продолжать диалог!
```

---

#### 2. Sliding Window

**Идея:** Хранить только последние N сообщений

**Преимущества:**

- ✅ Простая реализация
- ✅ Предсказуемое использование токенов

**Недостатки:**

- ❌ Теряет старый контекст ПОЛНОСТЬЮ

## 2️⃣ LONG-TERM MEMORY (Долгосрочная память)

### 📖 ОПРЕДЕЛЕНИЕ

**Long-Term Memory (LTM)** — это память **вне контекста**, хранящаяся в **внешней базе данных** (обычно Vector DB).

**Формула:**

```
Long-Term Memory = Vector Database (Embeddings)
```

**Ключевая идея:**

- Старые сообщения → Embeddings (векторы)
- Сохранить в Vector DB (Pinecone, Chroma, Weaviate)
- При новом запросе → Найти похожие (semantic search)
- Добавить в контекст

---

### 🧠 КАК РАБОТАЕТ

**Архитектура:**

```
┌─────────────────────┐
│ User Query          │
│ "Расскажи про RAG"  │
└──────────┬──────────┘
           │
           ▼
┌─────────────────────┐
│ Embedding Model     │
│ text → vector       │
└──────────┬──────────┘
           │
           ▼
┌─────────────────────┐
│ Vector Database     │
│ Search similar      │
│ vectors             │
└──────────┬──────────┘
           │
           ▼
┌─────────────────────┐
│ Top-K Results       │
│ (3-5 relevant docs) │
└──────────┬──────────┘
           │
           ▼
┌─────────────────────┐
│ LLM (GPT-4)         │
│ Context: Query +    │
│ Retrieved docs      │
└──────────┬──────────┘
           │
           ▼
┌─────────────────────┐
│ Answer              │
└─────────────────────┘
```

## ⚠️ ПРОБЛЕМЫ И ВЫЗОВЫ

### 1️⃣ Privacy (Конфиденциальность)

**Проблема:**

```
Все ваши сообщения → Vector DB → Храниться вечно
Что если утечка?
```

**Решения:**

- **On-Device Vector DB** (хранить локально)
- **Encryption** (шифрование)
- **Federated Learning** (данные не покидают устройство)

---

### 2️⃣ Data Leakage (Утечка данных между пользователями)

**Проблема:**

```
User A: "Мой пароль: qwerty123"
→ Сохранено в Vector DB

User B: "Какие пароли используют люди?"
→ Vector DB возвращает "qwerty123" из истории User A

❌ УТЕЧКА!
```

**Решение:**

- **User Isolation** — фильтр по user_id
- **Sensitive Data Detection** — не сохранять пароли, секреты

---

### 3️⃣ Cost (Стоимость)

**Проблема:**

```
Vector DB (Pinecone):
- Storage: $0.096/GB/месяц
- Queries: $0.0004 / query

100K пользователей × 1 GB памяти каждый = 100 TB
→ $9,600/месяц только за хранение
→ $$$
```

**Решение:**

- **Compression** (сжатие старых диалогов)
- **Expiry** (удаление после N месяцев)
- **Self-Hosted** (Chroma, Weaviate)

### 📖 КОНЦЕПТУАЛЬНАЯ МОДЕЛЬ ПАМЯТИ

**Память AI-агента** — это многоуровневая система хранения и извлечения информации, вдохновленная когнитивной психологией и адаптированная под архитектурные ограничения языковых моделей.

---

### 1️⃣ ТИПЫ ПАМЯТИ В AI-АГЕНТАХ

#### Краткосрочная память (Short-Term Memory, STM)

**Определение:** Временное хранилище информации в пределах активного контекста обработки.

**Характеристики:**

- **Размер:** Ограничен размером контекстного окна модели (4K-2M tokens)
- **Длительность:** Существует только в рамках текущей сессии
- **Скорость доступа:** Мгновенный (O(1) по времени)
- **Формат:** Сырой текст в контексте

**Механизм работы:**

```
┌─────────────────────────────────────────┐
│  Контекстное окно (8K tokens)           │
│                                         │
│  [System Prompt]        500 tokens      │
│  [User Message 1]       200 tokens      │
│  [Assistant Response]   300 tokens      │
│  [User Message 2]       150 tokens      │
│  ...                                    │
│  [Current Processing]   ~1000 tokens    │
│                                         │
│  Доступная память: 5,850 / 8,000 tokens │
└─────────────────────────────────────────┘
```

**Преимущества:**

- ✅ Не требует дополнительной инфраструктуры
- ✅ Полный контроль контекста (модель "видит" всё)
- ✅ Нулевая задержка на извлечение

**Ограничения:**

- ❌ Фиксированный размер (hard limit)
- ❌ Линейное увеличение стоимости с ростом контекста
- ❌ Потеря информации при переполнении

---

#### Рабочая память (Working Memory)

**Определение:** Активное подмножество краткосрочной памяти, используемое для текущей задачи.

**Концепция:**

```
Краткосрочная память (8K tokens)
    │
    └─→ Рабочая память (2K tokens)
        - Текущий запрос пользователя
        - Релевантный контекст для ответа
        - Промежуточные вычисления
```

**Пример:**

```
Задача: "Проанализируй этот код и найди баги"

Рабочая память включает:
- Код для анализа (500 tokens)
- Правила поиска багов (300 tokens)
- Промежуточные результаты анализа (200 tokens)
- Формирование ответа (1000 tokens)

Не включает:
- Предыдущие 10 сообщений о других темах
- System prompt (используется, но не в активной обработке)
```

**Механизм:**

- **Attention Mechanism** фокусирует вычислительные ресурсы на релевантной части контекста
- **Query-Key-Value** трансформация извлекает нужные фрагменты

---

#### Долгосрочная память (Long-Term Memory, LTM)

**Определение:** Внешнее хранилище информации, доступное через механизмы поиска и извлечения (retrieval).

**Характеристики:**

- **Размер:** Практически неограничен (зависит от инфраструктуры)
- **Длительность:** Персистентная (сохраняется между сессиями)
- **Скорость доступа:** Зависит от системы индексации (10-100ms для vector search)
- **Формат:** Embeddings (векторные представления)

**Архитектура хранения:**

```
┌──────────────────────────────────────────┐
│  Vector Database (Pinecone/Chroma)       │
│                                          │
│  Document 1:                             │
│    - Text: "Пользователь Python dev"    │
│    - Embedding: [0.23, -0.56, ...]      │
│    - Metadata: {timestamp, user_id}     │
│                                          │
│  Document 2:                             │
│    - Text: "Работает в AI стартапе"     │
│    - Embedding: [0.18, -0.43, ...]      │
│    - Metadata: {timestamp, user_id}     │
│                                          │
│  ... (миллионы документов)               │
└──────────────────────────────────────────┘
```

**Процесс извлечения (Retrieval):**

```
1. Query: "Что пользователь говорил про свою работу?"
   ↓
2. Query Embedding: [0.21, -0.48, ...] (384-1536 dimensions)
   ↓
3. Vector Similarity Search (Cosine/Euclidean):
   distance(query_emb, doc_emb) → Top-K results
   ↓
4. Retrieved Documents:
   - Doc 2: "Работает в AI стартапе" (similarity: 0.87)
   - Doc 15: "Интересуется ML" (similarity: 0.82)
   ↓
5. Add to Context Window:
   [Query] + [Retrieved Docs] → LLM → Answer
```

### 2️⃣ КАК АГЕНТЫ ЗАПОМИНАЮТ И ИЗВЛЕКАЮТ ИНФОРМАЦИЮ

#### Процесс запоминания (Encoding)

**1. Semantic Chunking (Семантическое разбиение)**

Длинный текст → небольшие смысловые фрагменты:

```python
# Плохой подход: фиксированный размер
chunks = split_text(text, chunk_size=500)  # Может разорвать предложения

# Хороший подход: семантическое разбиение
chunks = semantic_chunking(text, model="sentence-transformer")
# → ["Абзац 1", "Абзац 2", "Список пунктов 1-3", ...]
```

**2. Embedding Generation (Создание векторных представлений)**

```python
from sentence_transformers import SentenceTransformer

model = SentenceTransformer('paraphrase-multilingual-MiniLM-L12-v2')

text = "Пользователь работает Python разработчиком"
embedding = model.encode(text)  # → [0.23, -0.56, 0.89, ...] (384 dims)
```

**3. Metadata Enrichment (Обогащение метаданными)**

```python
document = {
    "text": text,
    "embedding": embedding.tolist(),
    "metadata": {
        "timestamp": "2024-03-15T14:30:00Z",
        "user_id": "user_123",
        "session_id": "session_456",
        "memory_type": "semantic",  # episodic/semantic/procedural
        "importance": 0.8,  # 0-1 scale
        "source": "chat_message"
    }
}

vector_db.upsert([document])
```

#### Процесс извлечения (Retrieval)

**1. Hybrid Search (Гибридный поиск)**

Комбинация **semantic search** (векторное сходство) и **keyword search** (текстовый поиск):

```python
# Semantic Search
query_embedding = model.encode("Какой у пользователя опыт работы?")
semantic_results = vector_db.query(
    vector=query_embedding,
    top_k=5,
    filter={"user_id": "user_123"}  # Изоляция пользователей
)

# Keyword Search (BM25)
keyword_results = full_text_search("опыт работы разработчик")

# Hybrid Fusion
results = rerank(semantic_results + keyword_results)
```

**2. Contextual Reranking (Перестановка по релевантности)**

```python
# Проблема: векторный поиск может вернуть похожие, но не релевантные тексты
# Решение: reranking на основе контекста

from sentence_transformers import CrossEncoder

reranker = CrossEncoder('cross-encoder/ms-marco-MiniLM-L-6-v2')

# Пары: (query, candidate_text)
pairs = [(query, result.text) for result in results]
scores = reranker.predict(pairs)

# Сортировка по новым скорам
reranked = sorted(zip(results, scores), key=lambda x: x[1], reverse=True)
```

**3. Memory Consolidation (Консолидация памяти)**

Периодическое объединение похожих воспоминаний:

```python
# Каждые 100 сообщений:
# 1. Найти похожие embeddings (cluster analysis)
similar_memories = find_clusters(embeddings, threshold=0.9)

# 2. Объединить в summary
for cluster in similar_memories:
    summary = llm.summarize([mem.text for mem in cluster])
    new_memory = {
        "text": summary,
        "embedding": model.encode(summary),
        "metadata": {
            "type": "consolidated",
            "source_ids": [mem.id for mem in cluster],
            "importance": max([mem.importance for mem in cluster])
        }
    }
    vector_db.upsert([new_memory])
    # 3. Удалить старые (опционально)
    vector_db.delete([mem.id for mem in cluster])
```

#### Vector Databases: глубокое погружение

**1. Индексация (HNSW — Hierarchical Navigable Small World)**

```
Проблема: Linear search O(N) слишком медленный для миллионов векторов

Решение: HNSW — граф приближённого поиска

Структура:
┌────────────────────────────────────┐
│  Layer 2 (sparse, long edges)      │
│    • ────────────────→ •           │
│                                    │
├────────────────────────────────────┤
│  Layer 1 (medium density)          │
│    • ──→ • ──→ •                   │
│     ↓     ↓     ↓                  │
├────────────────────────────────────┤
│  Layer 0 (dense, all vectors)      │
│    • → • → • → • → • → •           │
└────────────────────────────────────┘

Поиск:
1. Start at top layer → greedy search to closest node
2. Move down → refine search
3. Layer 0 → exact neighbors

Сложность: O(log N) вместо O(N)
```

**2. Метрики сходства**

| Метрика         | Формула                     | Когда использовать                                    |
| --------------- | --------------------------- | ----------------------------------------------------- |
| **Cosine**      | `cos(θ) = (A·B) / (‖A‖‖B‖)` | Текст, семантика (direction важнее magnitude)         |
| **Euclidean**   | `√Σ(ai - bi)²`              | Embeddings от моделей с нормализацией                 |
| **Dot Product** | `Σ(ai × bi)`                | Ускоренная версия Cosine для нормализованных векторов |

**3. Сравнение Vector DB**

| База         | Тип         | Индекс   | Плюсы                  | Минусы            | Цена              |
| ------------ | ----------- | -------- | ---------------------- | ----------------- | ----------------- |
| **Pinecone** | Cloud       | HNSW     | Managed, быстрый       | Vendor lock-in    | $70+/мес          |
| **Chroma**   | Open-source | HNSW     | Бесплатный, простой    | Self-hosted       | $0 (хостинг свой) |
| **Weaviate** | Гибрид      | HNSW     | Гибридный поиск        | Сложная настройка | $0-200/мес        |
| **Qdrant**   | Open-source | HNSW     | Rust (быстро), фильтры | Меньше интеграций | $0 (self-host)    |
| **Milvus**   | Open-source | IVF/HNSW | Масштабируемый         | Сложная установка | $0 (self-host)    |

### 4️⃣ ПРОБЛЕМЫ ПАМЯТИ АГЕНТОВ

#### 1. Забывание (Catastrophic Forgetting)

**Проблема:**

```
День 1: Агент помнит, что пользователь любит Python
День 30: 1000+ новых сообщений
→ Старая информация вытеснена из контекста
→ Не извлечена из Vector DB (query не релевантен)
→ ЗАБЫТО
```

**Решения:**

**а) Importance Scoring (Оценка важности)**

```python
def calculate_importance(text, metadata):
    score = 0.5  # base

    # Явные маркеры
    if "важно" in text.lower():
        score += 0.3

    # Личная информация
    if any(word in text for word in ["люблю", "работаю", "живу"]):
        score += 0.2

    # Frequency (как часто упоминалось)
    score += min(metadata.get('mention_count', 0) * 0.05, 0.3)

    return min(score, 1.0)

# При retrieval: приоритет высоким scores
results = vector_db.query(
    vector=query_emb,
    filter={"importance": {"$gte": 0.7}}  # Только важные
)
```

**б) Periodic Review (Периодическое повторение)**

```python
# Каждые 7 дней: "review" старой важной информации
old_important = vector_db.query(
    filter={
        "importance": {"$gte": 0.8},
        "last_accessed": {"$lt": "7_days_ago"}
    }
)

# Добавить в контекст следующего сообщения
system_prompt += f"\nВажная информация из прошлого:\n{old_important}"
```

**в) Decay Function (Забывание со временем)**

```python
import math
from datetime import datetime, timedelta

def decay_importance(original_importance, timestamp):
    days_old = (datetime.now() - timestamp).days
    # Exponential decay: half-life = 30 days
    decay_factor = math.exp(-days_old / 30)
    return original_importance * decay_factor

# При retrieval учитывать decay
results_with_decay = [
    (doc, doc.importance * decay_factor(doc.timestamp))
    for doc in results
]
```

**Проблема:**

```
Сообщение 10: "Я работаю Python разработчиком"
Сообщение 500: "Я перешёл на Go разработку"

Query: "Какой язык программирования использует пользователь?"
```

**Решения:**

**а) Temporal Ordering (Временной приоритет)**

```python
# Приоритет новым данным при конфликте
results = vector_db.query(vector=query_emb, top_k=10)

# Группировка по теме
topics = group_by_topic(results)  # ML clustering

# Для каждой темы: выбрать самый свежий
resolved = [max(cluster, key=lambda x: x.timestamp) for cluster in topics]
```

**б) Explicit Updates (Явное обновление)**

```python
# Детектировать противоречия
if detect_contradiction(new_info, existing_memories):
    # Пометить старое как устаревшее

# При retrieval: фильтровать deprecated
results = vector_db.query(
    filter={"deprecated": {"$ne": True}}

```

**в) Confidence Scoring (Оценка уверенности)**

```python
memory_1 = {"text": "Работаю на Python", "confidence": 0.9}
memory_2 = {"text": "Перешёл на Go", "confidence": 0.95}

# LLM разрешает конфликт на основе confidence
```

#### 3. Переполнение памяти (Memory Overflow)

**Проблема:**

```
10K пользователей × 1000 сообщений каждый = 10M документов
Embeddings: 384 dims × 4 bytes = 1.5 KB / документ
→ 10M × 1.5 KB = 15 GB памяти
→ Pinecone: $144/месяц только за хранение
```

**Решения:**

**а) Compression (Сжатие)**

```python
# Quantization: float32 → int8
embeddings_int8 = (embeddings * 127).astype(np.int8)
# Размер: 384 dims × 1 byte = 384 bytes (4x меньше!)

# Dimensionality Reduction: PCA/UMAP
from sklearn.decomposition import PCA
pca = PCA(n_components=128)  # 384 → 128 dims
compressed = pca.fit_transform(embeddings)
# Размер: 3x меньше (с минимальной потерей точности)
```

**б) Tiered Storage (Многоуровневое хранение)**

```python
# Hot tier (частый доступ): Pinecone (быстро, дорого)
# Cold tier (редкий доступ): S3 + DuckDB (медленно, дешево)

if memory.access_count > 10:
    pinecone.upsert(memory)  # $$$
else:
    s3.upload(memory)  # $

# При retrieval:
results_hot = pinecone.query(...)
if len(results_hot) < top_k:
    results_cold = s3_search(...)  # Fallback
```

**в) Eviction Policy (Политика удаления)**

```python
# LRU (Least Recently Used)
if memory_usage > threshold:
    old_memories = vector_db.query(
        order_by="last_accessed",
        limit=1000
    )
    vector_db.delete([m.id for m in old_memories])

# LFU (Least Frequently Used)
if memory_usage > threshold:
    rare_memories = vector_db.query(
        order_by="access_count",
        limit=1000
    )
    vector_db.delete([m.id for m in rare_memories])
```

### 1. Типы памяти

**Вопрос 1.1:** В чём фундаментальное различие между краткосрочной (STM) и долгосрочной (LTM) памятью в AI-агентах?

<details>
<summary>Ответ</summary>

**Краткосрочная память (STM):**

- Хранится в контекстном окне модели (4K-2M tokens)
- Мгновенный доступ (O(1))
- Ограниченный размер (hard limit)
- Исчезает после сессии
- Формат: сырой текст

**Долгосрочная память (LTM):**

- Хранится в Vector Database (практически неограниченно)
- Доступ через retrieval (10-100ms)
- Масштабируемый размер
- Персистентная (сохраняется между сессиями)
- Формат: embeddings (векторы)

**Ключевое различие:** STM — это "что модель видит сейчас", LTM — это "что модель может найти при необходимости".

</details>

---

**Вопрос 1.2:** Объясните концепцию "рабочей памяти" (Working Memory) в контексте Transformer-архитектуры. Как механизм attention реализует эту концепцию?

<details>
<summary>Ответ</summary>

**Рабочая память** — это подмножество краткосрочной памяти, активно используемое для текущей задачи.

**Реализация через Attention:**

```
Input tokens: [T1, T2, T3, ..., T100]
Query (текущий токен): TN

Attention scores:
- T1: 0.05 (низкая релевантность)
- T2: 0.02
- T50: 0.45 (высокая релевантность!)
- T51: 0.38
- TN-1: 0.10

→ Модель "фокусируется" на T50, T51 (рабочая память)
→ Остальные токены "в фоне" (краткосрочная память)
```

**Механизм:**

1. **Query-Key matching** определяет релевантность каждого токена
2. **Softmax** нормализует scores (сумма = 1)
3. **Value weighting** взвешивает информацию по scores
4. Результат: агрегированное представление **релевантной** информации

**Аналогия:** Человек читает книгу. Вся книга в памяти (STM), но активно обрабатывается только текущий абзац (Working Memory).

</details>

### 2. Запоминание и извлечение

**Вопрос 2.1:** Опишите полный pipeline процесса запоминания информации в Vector Database. Какие этапы критичны для качества retrieval?

<details>
<summary>Ответ</summary>

**Pipeline запоминания:**

1. **Chunking (Разбиение):**

   - Текст → смысловые фрагменты (sentences/paragraphs)
   - Критично: не разрывать контекст (плохо: "Python хорош" / "для ML")

2. **Embedding Generation:**

   - Текст → вектор (384-1536 dims)
   - Критично: использовать ту же модель, что для query

3. **Metadata Enrichment:**

   - timestamp, user_id, importance, type
   - Критично: фильтрация для изоляции пользователей

4. **Indexing:**

   - Вставка в Vector DB (HNSW/IVF index)
   - Критично: выбор метрики (cosine для текста)

5. **Verification:**
   - Проверка: запрос → извлечение только что добавленного
   - Критично: выявление проблем индексации

**Критичные этапы для quality retrieval:**

- **Chunking:** определяет гранулярность поиска
- **Embedding model:** напрямую влияет на semantic similarity
- **Metadata:** позволяет фильтрацию и контекстуализацию
</details>

**Вопрос 2.2:** Что такое "гибридный поиск" (Hybrid Search)? Почему он превосходит чистый semantic search для многих задач?

<details>
<summary>Ответ</summary>

**Гибридный поиск** = Semantic Search (векторы) + Keyword Search (BM25/TF-IDF)

**Semantic Search:**

- Ищет по смыслу (synonyms, paraphrases)
- Пример: "машина" найдёт "автомобиль", "авто"
- Проблема: плохо работает с точными терминами ("GPT-4", "Python 3.12")

**Keyword Search:**

- Ищет точные совпадения слов
- Пример: "Python 3.12" найдёт только "Python 3.12"
- Проблема: не понимает synonyms ("машина" НЕ найдёт "автомобиль")

**Hybrid:**

```python
# Пример: "Проблемы с установкой Python 3.12 на MacOS"

# Semantic Search найдёт:
- "Ошибки при установке Python на Mac" (synonyms)
- "Как установить Python на MacOS" (paraphrase)

# Keyword Search найдёт:
- Точно "Python 3.12" (не 3.11, не 3.10)
- Точно "MacOS" (не Windows, не Linux)

# Hybrid = пересечение/объединение с reranking
```

**Почему лучше:**

- ✅ Точность keywords + гибкость semantics
- ✅ Меньше false positives (semantic) и false negatives (keywords)
- ✅ 10-20% улучшение recall в бенчмарках
</details>

### 3. RAG и Vector Databases

**Вопрос 3.1:** Объясните, почему RAG (Retrieval-Augmented Generation) решает проблему "hallucinations" (галлюцинаций) LLM. Приведите конкретный пример.

<details>
<summary>Ответ</summary>

**Проблема галлюцинаций:**

```
User: "Какие требования к API в нашем проекте?"
LLM (без RAG): "API должен использовать GraphQL и поддерживать real-time"
→ HALLUCINATION (LLM придумал, т.к. нет данных)
```

**Решение через RAG:**

**Вопрос 3.2:** Сравните HNSW и IVF индексацию в Vector Databases. В каких сценариях предпочтительна каждая?

<details>
<summary>Ответ</summary>

| Параметр        | HNSW                        | IVF                             |
| --------------- | --------------------------- | ------------------------------- |
| **Структура**   | Граф (навигация по рёбрам)  | Кластеры (Voronoi диаграмма)    |
| **Поиск**       | Greedy graph traversal      | Ближайший кластер → linear scan |
| **Сложность**   | O(log N)                    | O(√N) для N/√N кластеров        |
| **Точность**    | Высокая (99%+ recall)       | Средняя (85-95% recall)         |
| **Скорость**    | Очень быстрая               | Быстрая                         |
| **Память**      | Высокая (граф + векторы)    | Средняя (центроиды + векторы)   |
| **Insert cost** | Высокая (перестройка графа) | Низкая (добавить в кластер)     |

**HNSW предпочтительна когда:**

- ✅ Нужна максимальная точность поиска (99%+ recall)
- ✅ Dataset статичный (редкие updates)
- ✅ Есть память для графа
- ✅ Примеры: production search, recommendation systems

**IVF предпочтительна когда:**

- ✅ Частые inserts/updates (динамичный dataset)
- ✅ Ограниченная память
- ✅ Допустима небольшая потеря точности (90% recall OK)
- ✅ Примеры: real-time streaming, prototyping

**Hybrid:**

- Некоторые DB (Milvus) комбинируют: IVF + HNSW внутри кластеров

```python
    new_info.supersedes = [c.id for c in conflicts]
    db.upsert(new_info)
```

```python
def answer_with_verification(query):
    results = retrieve(query)

    if not results:
        # Сохранить "negative evidence"
        db.upsert({
            "type": "query_without_answer",

    # Multi-source verification
    if len(results) >= 2 and all(r.score > 0.8 for r in results):

    elif results[0].score > 0.7:
        confidence = "medium"
    else:
        confidence = "low"

    answer = generate(query, results)

    return {
        "answer": answer,
        "confidence": confidence,
        "sources": [r.id for r in results]
    }
```
