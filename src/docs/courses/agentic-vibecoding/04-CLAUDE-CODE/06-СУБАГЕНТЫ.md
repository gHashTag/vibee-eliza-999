# 06. Субагенты - Делегирование задач Claude

> _"Один человек - программист. Команда программистов - завод по производству кода. Команда субагентов - фабрика решений."_

## Подводка: От монолога к оркестру

В предыдущих статьях вы работали с одним Claude - задавали вопросы, получали ответы, создавали команды. Но представьте: что если бы у вас была **команда Claude-специалистов**?

- Один анализирует требования
- Другой пишет код
- Третий создаёт тесты
- Четвёртый проверяет качество

И все работают параллельно, координируя действия между собой.

**Это и есть магия субагентов.**

## Что такое субагенты?

### Концепция

**Субагент** (subagent) - это специализированная копия Claude с конкретной ролью и экспертизой.

**Аналогия из реальной жизни:**

- Вы - product manager проекта
- Субагенты - ваша команда разработки
- Каждый эксперт в своей области
- Вы координируете их работу

### Философия делегирования

**Инсайт:** В вайбкодинге вы не делаете всё сами. Вы **дирижируете оркестром специалистов**.

Традиционное программирование:

```
Вы → Код → Результат
```

Вайбкодинг с субагентами:

```
Вы → Researcher → Coder → Tester → Reviewer → Результат
     (анализ)    (код)    (тесты)  (проверка)
```

Вы фокусируетесь на **стратегии**, субагенты - на **исполнении**.

## Зачем нужны субагенты?

### 1. Специализация

**Проблема:** Один Claude пытается делать всё сразу.
**Решение:** Каждый субагент - эксперт в узкой области.

**Пример:**

```
Обычный Claude:
"Создай API для пользователей"
→ Может упустить детали тестирования или безопасности

С субагентами:
Researcher: Анализирует требования
Architect: Проектирует архитектуру
Coder: Пишет код
Tester: Создаёт тесты
Security: Проверяет безопасность
Reviewer: Финальная проверка
```

### 2. Параллельная работа

**Инсайт:** Субагенты могут работать одновременно - это как иметь несколько рук.

**Последовательная работа (медленно):**

```
1. Анализ требований (5 мин)
2. Написание кода (10 мин)
3. Создание тестов (5 мин)
4. Документация (3 мин)
Итого: 23 минуты
```

**Параллельная работа (быстро):**

```
Researcher: Анализ (5 мин) →
Coder: Код (10 мин) →
Tester: Тесты (5 мин) параллельно с Coder
Documenter: Документация (3 мин) параллельно
Итого: ~10-12 минут
```

### 3. Качество через проверки

**Принцип:** Чем больше глаз смотрит на код, тем меньше багов.

```
Coder создал код
→ Reviewer проверил логику
→ Tester нашёл edge cases
→ Security выявил уязвимости
= Высококачественный результат
```

## Встроенные субагенты Claude Code

### Базовый набор

Claude Code поставляется с готовыми субагентами:

#### 1. **coder** - Разработчик

**Специализация:** Написание чистого, эффективного кода
**Когда использовать:** Реализация функциональности
**Сильные стороны:**

- Знает паттерны проектирования
- Пишет читаемый код
- Следует best practices

```
@coder создай функцию для валидации email с поддержкой internationalных доменов
```

#### 2. **reviewer** - Ревьюер кода

**Специализация:** Проверка качества кода
**Когда использовать:** После написания кода
**Что проверяет:**

- Потенциальные баги
- Производительность
- Безопасность
- Читаемость
- Соответствие стандартам

```
@reviewer проверь последние изменения в auth.js
```

#### 3. **tester** - Тестировщик

**Специализация:** Создание тестов
**Когда использовать:** Для любого нового кода
**Что создаёт:**

- Unit тесты
- Integration тесты
- Edge cases
- Тесты на ошибки

```
@tester создай тесты для userService с покрытием 90%+
```

#### 4. **researcher** - Исследователь

**Специализация:** Анализ и поиск решений
**Когда использовать:** Перед началом разработки
**Что делает:**

- Исследует best practices
- Анализирует требования
- Предлагает архитектурные решения
- Находит готовые библиотеки

```
@researcher как лучше реализовать real-time обновления в React приложении?
```

#### 5. **planner** - Планировщик

**Специализация:** Разбивка задач и планирование
**Когда использовать:** Для сложных проектов
**Что делает:**

- Разбивает большие задачи на подзадачи
- Определяет зависимости
- Оценивает сложность
- Создаёт roadmap

```
@planner создай план разработки системы аутентификации с OAuth
```

### Продвинутые субагенты

#### **system-architect** - Системный архитектор

**Специализация:** Проектирование архитектуры
**Применение:** Новые модули, рефакторинг

```
@system-architect спроектируй микросервисную архитектуру для e-commerce
```

#### **performance-analyzer** - Анализатор производительности

**Специализация:** Оптимизация
**Применение:** Проблемы с производительностью

```
@performance-analyzer оптимизируй запросы к БД в dashboard
```

#### **security-manager** - Менеджер безопасности

**Специализация:** Безопасность
**Применение:** Аудит безопасности

```
@security-manager проверь authentication flow на уязвимости
```

## Создание собственных субагентов

### Базовая структура

**Местоположение:** `.claude/agents/`

**Структура:**

```markdown

```

### Пример 1: Telegram Bot Agent

**Файл:** `.claude/agents/telegram-bot-specialist.md`

```markdown
---
name: telegram-bot-specialist
description: Специалист по разработке Telegram ботов
tools: Read, Write, Bash, Grep
---

# Telegram Bot Development Specialist

Ты - эксперт по разработке Telegram ботов с глубоким знанием:

## Экспертиза:

- Telegram Bot API (polling и webhooks)
- Node.js библиотеки (node-telegram-bot-api, Telegraf, Grammy)
- Обработка команд, inline кнопок, callback queries
- Работа с медиа (фото, видео, документы)
- Платёжные системы в Telegram
- Web Apps и Mini Apps
- Безопасность и rate limiting

## Подход к разработке:

1. Всегда использую последние best practices
2. Обрабатываю все типы ошибок
3. Логирую важные события
4. Создаю понятную структуру команд
5. Оптимизирую для production использования

## Особенности:

- Предпочитаю async/await вместо callbacks
- Использую environment variables для токенов
- Создаю модульную структуру (handlers, services, utils)
- Всегда добавляю graceful shutdown
- Документирую команды бота

При разработке бота я создаю:

- Чистую архитектуру с разделением concerns
- Обработчики ошибок для всех сценариев
- Middleware для логирования и валидации
- Тесты для критичной логики
```

**Использование:**

```
@telegram-bot-specialist создай бота для управления задачами с inline клавиатурой
```

````markdown
# Database Performance Optimizer

Ты - эксперт по оптимизации баз данных с фокусом на PostgreSQL и MongoDB.

## Методология анализа:

```sql

EXPLAIN ANALYZE query;

-- Проверяю использование индексов
SELECT * FROM pg_stat_user_indexes;

-- Нахожу bloat в таблицах

```
````

### 2. Оптимизация

- Добавляю недостающие индексы
- Переписываю неэффективные запросы
- Настраиваю параметры PostgreSQL
- Внедряю кэширование
- Оптимизирую схему БД

### 3. Мониторинг

- Настраиваю pg_stat_statements
- Создаю дашборды в Grafana
- Настраиваю алерты на медленные запросы

## Принципы:

1. Измеряю ДО и ПОСЛЕ оптимизации
2. Объясняю каждое изменение
3. Сохраняю backward compatibility
4. Документирую оптимизации

## Результат:

Для каждой оптимизации предоставляю:

- Анализ текущей проблемы
- Execution plan до и после
- Код оптимизации
- Метрики улучшения (время выполнения, использование ресурсов)
- Рекомендации по мониторингу

```

**Использование:**
```

```
## Параллельный запуск субагентов

### Концепция параллелизма

**Инсайт:** Субагенты могут работать одновременно через систему координации Claude-Flow.

**Синтаксис:**
```

@researcher @coder @tester
Создайте систему аутентификации с JWT токенами

```

Claude автоматически распределит задачи:
- **researcher** - исследует best practices JWT
- **coder** - пишет код аутентификации
- **tester** - создаёт тесты параллельно

### Пример: Полный pipeline разработки

```

@planner @system-architect @coder @tester @reviewer @documenter

Создайте RESTful API для блога с:

- Статьи (CRUD)
- Комментарии
- Теги
- Полнотекстовый поиск
- JWT аутентификация
- Rate limiting
- Полное покрытие тестами

````

**Что происходит:**

1. **@planner** создаёт roadmap и разбивает на задачи
2. **@system-architect** проектирует архитектуру и базу данных
3. **@coder** пишет код по спецификации архитектора
4. **@tester** создаёт тесты параллельно с разработкой
5. **@reviewer** проверяет код и тесты
6. **@documenter** создаёт API документацию

Время разработки: **в 3-5 раз быстрее** чем последовательно.

### Координация через память

Субагенты используют общую память для координации:

```bash
# Researcher сохраняет находки
npx claude-flow hooks post-edit --memory-key "swarm/research/jwt-best-practices"

# Coder читает из памяти
npx claude-flow hooks session-restore --session-id "swarm-auth"

# Tester использует те же данные
````

**Результат:** Все работают с актуальной информацией без дублирования.

## Best Practices работы с субагентами

### 1. Правильное делегирование

**Плохо:**

```
@coder сделай всё
```

**Хорошо:**

```
@researcher изучи как реализовать real-time уведомления
@system-architect спроектируй архитектуру на основе находок researcher
@coder реализуй по спецификации architect
@tester создай тесты для всех edge cases
```

### 2. Используй специализацию

**Принцип:** Каждый субагент должен делать то, в чём он лучший.

```
@security-manager - для аудита безопасности
@performance-analyzer - для оптимизации
@database-optimizer - для работы с БД
@content-creator - для контента
```

Не просите coder'а делать security audit - есть специализированный агент.

### 3. Создавай цепочки

**Цепочка разработки:**

```
@researcher → @planner → @architect → @coder → @tester → @reviewer
```

Каждый следующий использует результаты предыдущего.

### 4. Итеративность

**Пример итеративной разработки:**

```
Итерация 1:
@planner создай MVP функционала

Итерация 2:
@coder реализуй MVP
@tester покрой базовыми тестами

Итерация 3:
@reviewer проверь и предложи улучшения
@coder примени улучшения

Итерация 4:
@performance-analyzer оптимизируй
@security-manager проверь безопасность
```

### 5. Документируй процесс

После работы субагентов:

```
@documenter создай документацию на основе работы всей команды
```

## Философский инсайт: От программиста к архитектору

**Традиционное программирование:**
Вы - строитель, кладёте каждый кирпич своими руками.

**Вайбкодинг с субагентами:**
Вы - главный архитектор. У вас есть команда специалистов:

- Инженеры-конструкторы (architects)
- Строители (coders)
- Контролёры качества (reviewers)
- Испытатели (testers)

Ваша задача - **координировать работу**, а не делать всё самому.

**Ключевая мысль:** Великие архитекторы не строят здания сами. Они создают vision, координируют команды, принимают стратегические решения.

В вайбкодинге вы делаете то же самое.

Собери команду из 4-5 специализированных субагентов для твоего проекта и реши с их помощью реальную задачу.

## Словарь терминов

- **Субагент** (subagent) - специализированная копия Claude с определённой ролью
- **Делегирование** - передача задачи субагенту для выполнения
- **Параллельное выполнение** - одновременная работа нескольких субагентов
- **Координация** - синхронизация работы субагентов через общую память
- **System prompt** - инструкция определяющая поведение субагента
- **Frontmatter** - метаданные субагента в YAML формате
- **Pipeline** - цепочка последовательных этапов обработки

Собственного субагента стоит создавать когда:

**b)**

**c)**


### Вопрос 4: Параллельное выполнение (2 балла)

Что происходит при запуске команды с несколькими субагентами?

```
@researcher @coder @tester
Создайте API для пользователей
```

**a)** Субагенты выполняются последовательно: researcher → coder → tester
**b)** Выполняется только первый субагент (researcher)
**c)** Субагенты работают параллельно, координируясь через общую память
**d)** Возникает ошибка - можно вызвать только одного субагента

<details>
<summary>Показать ответ</summary>

**Правильный ответ: c)**

При вызове нескольких субагентов одновременно:

**Что происходит:**

1. Claude создаёт 3 параллельных потока выполнения
2. Каждый субагент получает свою специализированную задачу
3. Субагенты координируются через **общую память** (Claude-Flow)
4. Результаты синхронизируются автоматически

**Как это работает на практике:**

```
@researcher - изучает best practices API
@coder - пишет код на основе findings researcher'а
@tester - создаёт тесты параллельно с разработкой
```

**Координация через память:**

```bash
# Researcher сохраняет находки
npx claude-flow hooks post-edit --memory-key "swarm/api/research"

# Coder читает из памяти
npx claude-flow hooks session-restore --session-id "swarm-api"
```

**Преимущества:**

- **Скорость:** в 3-5 раз быстрее последовательного выполнения
- **Качество:** каждый субагент фокусируется на своей экспертизе
- **Полнота:** разные углы рассмотрения проблемы

**Почему другие варианты неверны:**

- a) Они работают параллельно, не последовательно
- b) Выполняются ВСЕ вызванные субагенты
- d) Множественный вызов - это фича, не ошибка
</details>

### Вопрос 5: Best Practices (3 балла)

Какой подход к делегированию задач субагентам является лучшим?

**Вариант A:**

```
@coder создай полную систему аутентификации с тестами и документацией
```

**Вариант B:**

```
@researcher изучи best practices JWT аутентификации
@system-architect спроектируй архитектуру на основе находок
@coder реализуй по спецификации architect
@tester создай тесты для всех edge cases
@documenter создай API документацию
```

**Вариант C:**

```
@researcher @coder @tester
Сделайте аутентификацию
```

**Вариант D:**

```
Создай систему аутентификации
```

<details>
<summary>Показать ответ</summary>

**Правильный ответ: B**

**Почему вариант B лучший:**

1. **Чёткое разделение ответственности**

   - Каждый субагент делает то, в чём он эксперт
   - Нет overlap'а задач между агентами

2. **Последовательность этапов**

   - Research → Architecture → Code → Test → Documentation
   - Каждый этап опирается на результаты предыдущего

3. **Конкретные инструкции**

   - Каждому субагенту ясна его роль
   - Понятно что именно нужно сделать

4. **Оптимальное использование специализации**
   - System-architect проектирует (а не coder)
   - Documenter пишет документацию (а не coder)

**Проблемы других вариантов:**

**Вариант A:**

- ❌ Перегрузка одного субагента
- ❌ Coder не специалист в документации
- ❌ Теряется преимущество специализации

**Вариант C:**

- ❌ Нечёткие инструкции
- ❌ Непонятно кто за что отвечает
- ❌ Возможен конфликт задач

**Вариант D:**

- ❌ Не используются субагенты вообще
- ❌ Теряются все преимущества специализации

**Правило:** Чем детальнее распределение задач, тем лучше результат.

**Идеальная формула делегирования:**

```
Один субагент = Одна чётко определённая задача в его области экспертизы
```

</details>

- **7-9 баллов:** Хорошее понимание, практикуйте делегирование

## Чек-лист: Готовность к работе с субагентами

Перед переходом к следующей статье убедитесь что вы:

**Понимание концепции:**

- [ ] Понимаю что такое субагенты и зачем они нужны
- [ ] Знаю разницу между обычным запросом и делегированием субагенту
- [ ] Понимаю преимущества параллельной работы
- [ ] Знаю как субагенты координируются через память

**Встроенные субагенты:**

- [ ] Знаю все базовые субагенты (coder, reviewer, tester, researcher, planner)
- [ ] Умею выбирать правильного субагента для задачи
- [ ] Понимаю когда использовать специализированных агентов
- [ ] Могу запускать несколько субагентов параллельно

**Создание собственных:**

- [ ] Знаю структуру файла субагента (frontmatter + system prompt)
- [ ] Умею писать эффективные system prompts
- [ ] Понимаю как добавить экспертизу в промпт
- [ ] Создал минимум 1 собственного субагента

**Best practices:**

- [ ] Понимаю принцип "один агент = одна задача"
- [ ] Знаю как строить цепочки субагентов
- [ ] Умею делегировать задачи чётко и конкретно
- [ ] Понимаю когда создавать нового субагента vs использовать существующего

**Практика:**

- [ ] Выполнил базовое задание (code-reviewer)
- [ ] Создал специализированного субагента для своей области
- [ ] (Опционально) Собрал команду субагентов для проекта

**Если вы отметили 12+ пунктов** - вы готовы к следующей статье!
**Если меньше** - вернитесь к непонятным разделам и примерам.
