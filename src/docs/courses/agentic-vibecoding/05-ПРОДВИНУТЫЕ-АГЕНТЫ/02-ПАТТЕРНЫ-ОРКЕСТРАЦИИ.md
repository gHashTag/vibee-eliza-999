# ПАТТЕРНЫ ОРКЕСТРАЦИИ

> "Оркестр без дирижёра — шум. Оркестр с дирижёром — симфония."

## Что такое паттерн оркестрации?

**Паттерн** — это проверенный способ организации работы агентов.

**Аналогия: Рецепт приготовления блюда**

- Ингредиенты = агенты
- Последовательность действий = паттерн
- Результат = готовый проект

**Зачем нужны паттерны?**

- Не изобретать велосипед заново
- Использовать проверенные решения
- Понимать, что выбрать для своей задачи
- Экономить время на проектирование

## 5 основных паттернов

```
1. Sequential (Конвейер)    →  →  →  →
2. Parallel (Параллельный)  ↓  ↓  ↓  ↓
3. Group Chat (Совещание)   ↔  ↔  ↔  ↔
4. Hierarchical (Иерархия)  🏢
5. Event-Driven (Реакция)   ⚡
```

---

## Паттерн 1: Sequential (Конвейер)

### Как работает

```
Агент А → Агент Б → Агент В → Агент Г → Результат
```

Каждый агент:

1. Получает результат предыдущего
2. Делает свою работу
3. Передаёт следующему

### Аналогия: Строительство дома

```
Фундамент → Стены → Крыша → Отделка → Готовый дом
```

Нельзя ставить крышу до стен! Каждый этап зависит от предыдущего.

### Когда использовать

✅ **Подходит для:**

- CI/CD пайплайнов (тест → сборка → деплой)
- Обработки данных (загрузка → очистка → анализ → отчёт)
- Создания контента (идея → текст → редактура → публикация)
- Разработки функции (дизайн → код → тест → ревью)

❌ **НЕ подходит для:**

- Независимых задач, которые можно делать параллельно
- Ситуаций, когда нужна скорость
- Когда агенты не зависят друг от друга

### Пример: Создание статьи

```
1. Researcher (30 мин)
   "Изучил тему, нашёл 5 источников"
   ↓ передаёт найденные материалы

2. Outline Creator (15 мин)
   "Создал структуру из 7 разделов"
   ↓ передаёт план статьи

3. Writer (60 мин)
   "Написал 2000 слов по плану"
   ↓ передаёт черновик

4. Editor (20 мин)
   "Исправил 15 ошибок, улучшил стиль"
   ↓ передаёт отредактированный текст

5. Formatter (10 мин)
   "Добавил картинки, форматирование"
   ↓
✅ Готовая статья!

Итого: 135 минут (2 часа 15 минут)
```

**Что важно:**

- Каждый следующий агент улучшает результат предыдущего
- Нельзя пропустить этап
- Качество растёт на каждом шаге

### Плюсы и минусы

**Плюсы:**

- ✅ Предсказуемо — знаешь, что за чем идёт
- ✅ Легко отследить прогресс — видно на каком этапе
- ✅ Качество растёт с каждым шагом
- ✅ Просто понять и объяснить

**Минусы:**

- ❌ Медленно — ждём каждого агента
- ❌ Один сломался = всё стоит
- ❌ Не используется параллелизм
- ❌ Bottleneck на медленных этапах

### Как настроить

1. **Определи этапы** — что должно идти за чем
2. **Назначь агента на каждый этап** — кто что делает
3. **Определи формат передачи** — что именно передаём
4. **Настрой обработку ошибок** — что делать, если этап сломался

**Пример плохой последовательности:**

```
❌ Редактура → Написание → Исследование
(Невозможно редактировать то, чего нет!)
```

**Пример правильной последовательности:**

```
✅ Исследование → Написание → Редактура
(Логично и выполнимо!)
```

## Паттерн 2: Parallel (Параллельный)

### Как работает

```
              Задача
           ↙   ↓   ↓   ↘
        А₁    А₂   А₃   А₄
           ↘   ↓   ↓   ↙
            Результаты
```

Все агенты работают ОДНОВРЕМЕННО, потом собираем результаты.

### Аналогия: Ресторан

```
Заказ: Борщ + Салат + Десерт + Напиток

Повар 1: Варит борщ     (20 мин) ┐
Повар 2: Режет салат    (10 мин) ├─ Параллельно!
Повар 3: Делает десерт  (15 мин) │
Бармен:  Готовит кофе   (5 мин)  ┘

Итого: 20 минут (время самого долгого)
Вместо: 50 минут (если последовательно)

Ускорение: 2.5 раза! ⚡
```

### Когда использовать

✅ **Подходит для:**

- Независимых задач, которые не связаны
- Time-critical операций (нужно быстро)
- Получения разных перспектив на одну проблему
- Исследования альтернативных решений

❌ **НЕ подходит для:**

- Последовательных зависимостей (одно требует другое)
- Ограниченных ресурсов (мало памяти/CPU)
- Ситуаций, когда нужен один подход

### Пример: Разработка MVP

```
[Задача: Создать MVP за 2 недели]

         Старт (день 0)
            ↓
    ┌──────┼──────┬─────────┐
    ↓      ↓      ↓         ↓
Backend  Frontend Database  DevOps
(14 дней)(14 дней)(14 дней)(14 дней)
    ↘      ↓      ↓         ↙
         День 14: Интеграция
                ↓
            Готовый MVP ✅

Выигрыш: 14 дней вместо 56 дней!
Ускорение: 4 раза! 🚀
```

### Паттерн выбора победителя

Полезная вариация для принятия решений:

```
     Задача: "Как решить проблему X?"
         ↓
    ┌───┼───┬───┐
Expert₁ E₂ E₃ E₄  ← Каждый предлагает своё решение
    ↘   ↓  ↓  ↙
      Голосование или выбор лучшего
         ↓
    Лучшее решение
```

**Пример: Code review от 3 экспертов**

- Security Expert: "Добавь валидацию входных данных"
- Performance Expert: "Оптимизируй запросы к базе"
- UX Expert: "Улучши сообщения об ошибках"

**Результат:** Код проверен со всех точек зрения!

### Плюсы и минусы

**Плюсы:**

- ✅ Быстро — в 3-5 раз быстрее последовательного
- ✅ Эффективно используем время
- ✅ Разные точки зрения на проблему
- ✅ Легко масштабировать (добавить агентов)

**Минусы:**

- ❌ Сложнее координация
- ❌ Нужна интеграция результатов
- ❌ Может быть конфликт подходов
- ❌ Дороже (больше агентов работает одновременно)

### Типичные ошибки

**Ошибка 1: Скрытые зависимости**

```
❌ Параллельно: Frontend + Backend
Но: Frontend нужен API контракт от Backend!
```

**Решение:**

```
✅ Сначала: API дизайн
Потом параллельно: Frontend + Backend (по контракту)
```

**Ошибка 2: Несовместимые результаты**

```
❌ 3 дизайнера создали 3 разных стиля
Результат: несогласованный дизайн
```

**Решение:**

```
✅ Дать общий дизайн-гайд перед стартом
```

## Паттерн 3: Group Chat (Совещание)

### Как работает

```
    Агент А: "Предлагаю подход X"
       ↓
    Агент Б: "Подход X не сработает, потому что..."
       ↓
    Агент В: "А что если модифицировать X?"
       ↓
    Агент А: "Отличная идея! Добавим Y"
       ↓
    ✅ Консенсус достигнут!
```

Агенты **обсуждают** решение, пока не придут к согласию.

### Аналогия: Мозговой штурм

```
Маркетолог: "Давайте запустим рекламу в Instagram"
Финансист: "Бюджет только $1000"
Дизайнер: "Тогда сделаем серию из 10 простых постов"
Копирайтер: "Могу написать тексты за 3 дня"
Менеджер: "Окей, план: 10 постов, старт в понедельник"

✅ Решение найдено коллективно!
```

### Когда использовать

✅ **Подходит для:**

- Brainstorming (генерация идей)
- Сложных решений (нужны разные эксперты)
- Code review (несколько ревьюеров обсуждают)
- Споров (разрешение конфликтов подходов)
- Архитектурных решений

❌ **НЕ подходит для:**

- Простых задач (овер-инжиниринг)
- Срочных решений (долго обсуждают)
- Чётко определённого пути (незачем спорить)

### Пример: Архитектурное решение

```
[Задача: Выбрать базу данных для проекта]

Минута 0:
Backend Dev: "Нужна база данных. Предлагаю PostgreSQL"

Минута 2:
DB Architect: "Почему не MongoDB? У нас гибкая схема"

Минута 5:
DevOps: "PostgreSQL проще деплоить на нашем стеке"

Минута 8:
Backend Dev: "Согласен. Плюс у команды уже есть опыт с Postgres"

Минута 10:
DB Architect: "Хорошо, но давайте добавим JSONB колонки для гибкости"

Минута 12:
DevOps: "Поддерживаю. Получаем лучшее из обоих миров"

Минута 15:
✅ Решение: PostgreSQL с JSONB полями
   Все согласны! ✋✋✋
```

### Паттерн голосования

Полезная техника для быстрого решения:

```
Вопрос: "Какой фреймворк использовать?"

React:   👍👍👍 (3 голоса)
Vue:     👍 (1 голос)
Angular: (0 голосов)

Победитель: React ✅
```

### Плюсы и минусы

**Плюсы:**

- ✅ Коллективный разум — умнее, чем один эксперт
- ✅ Меньше ошибок (много глаз видят больше)
- ✅ Находит неочевидные решения
- ✅ Прозрачность (видно, кто что сказал)
- ✅ Buy-in от всех участников

**Минусы:**

- ❌ Долго (нужно время на обсуждение)
- ❌ Может быть бесконечный спор
- ❌ Сложно для простых задач
- ❌ Риск "group thinking" (все соглашаются с лидером)

### Техники управления дискуссией

**1. Timeboxing**

```
Правило: Обсуждение максимум 30 минут
Если нет решения → голосование
```

**2. Модератор**

```
Один агент = модератор
Следит за:
- Все высказались
- Нет зацикливания
- Движение к решению
```

**3. Асинхронная дискуссия**

```
Не real-time чат, а:
1. Каждый пишет своё мнение
2. Читают мнения других
3. Корректируют своё
4. Голосование
```

## Паттерн 4: Hierarchical (Иерархия)

### Как работает

```
          [CEO Agent]
         "Цель: Запустить продукт"
              ↓
      ┌──────┴──────┐
[Tech Lead]    [Product Lead]
      ↓              ↓
   ┌──┴──┐       ┌──┴──┐
[Dev] [QA]   [Design] [Marketing]
```

Иерархия уровней: верхние дают задачи, нижние выполняют.

### Аналогия: Армия

```
Генерал: "Взять высоту 101"
   ↓ декомпозирует задачу
Полковник: "1-й батальон слева, 2-й справа"
   ↓ детализирует план
Капитан: "1-й взвод прикрытие, 2-й атака"
   ↓ конкретные приказы
Солдаты: Выполняют действия

Каждый уровень детализирует задачу!
```

### Когда использовать

✅ **Подходит для:**

- Больших проектов (10+ агентов)
- Сложной декомпозиции задач
- Чёткой иерархии ответственности
- Enterprise решений
- Долгосрочных проектов

❌ **НЕ подходит для:**

- Простых задач (овер-инжиниринг)
- Быстрых решений (медленная коммуникация)
- Творческих задач (нужна свобода)
- Маленьких команд (избыточно)

### Пример: Разработка SaaS платформы

```
[Project Manager]
"Создать SaaS для управления проектами за 6 месяцев"
         ↓
    ┌────┴────┬────────┬────────┐
[Backend]  [Frontend] [Infra]  [Product]
Lead       Lead       Lead      Lead
    ↓         ↓          ↓        ↓
┌───┼───┐  ┌──┼──┐   ┌──┼──┐  ┌─┼─┐
API  DB   UI Mobile Cloud DevOps UX Design
Dev  Dev  Dev Dev   Eng  Eng   Designer
```

**Поток задачи:**

```
PM: "Нужна функция экспорта данных"
  ↓
Backend Lead: "Разделим: API эндпоинт + генерация файлов"
  ↓
API Dev: "Создаю /export endpoint"
DB Dev: "Оптимизирую запрос для больших данных"
  ↓
✅ Готово на всех уровнях
```

### Уровни абстракции

```
Уровень 1 (PM):
"Добавить систему уведомлений"

Уровень 2 (Tech Lead):
"Email уведомления + Push + In-app"

Уровень 3 (Backend Dev):
"Настрою SendGrid для email"

Уровень 4 (Junior Dev):
"Создаю email шаблоны"
```

Каждый уровень более конкретен!

### Плюсы и минусы

**Плюсы:**

- ✅ Масштабируется до любых размеров
- ✅ Чёткая ответственность
- ✅ Понятная структура
- ✅ Работает для больших команд
- ✅ Легко добавлять новых агентов

**Минусы:**

- ❌ Медленные решения (много уровней)
- ❌ Бюрократия
- ❌ Может быть bottleneck на уровнях
- ❌ Потеря контекста между уровнями

### Антипаттерны

**Антипаттерн 1: Слишком много уровней**

```
❌ CEO → VP → Director → Manager → Team Lead → Senior → Junior
(7 уровней для простой задачи!)

✅ CEO → Team Lead → Developer
(3 уровня достаточно)
```

**Антипаттерн 2: Micromanagement**

```
❌ PM диктует каждую строку кода

✅ PM задаёт цель, разработчики решают как
```

## Паттерн 5: Event-Driven (Реакция на события)

### Как работает

```
Событие происходит
      ↓
Агенты реагируют автоматически

Пример:
Файл загружен → Вирус скан → Превью → Уведомление
```

Агенты не ждут команд, а **реагируют на события**.

### Аналогия: Пожарная служба

```
🔥 Сигнал пожара (событие)
      ↓
🚒 Пожарные выезжают (реакция)
      ↓
💦 Тушат пожар (действие)
      ↓
✅ Новое событие: "Пожар потушен"
      ↓
🚑 Медики проверяют пострадавших (реакция)

Никто не командует — каждый знает, что делать при событии!
```

### Когда использовать

✅ **Подходит для:**

- Reactive систем
- Webhooks
- Real-time обработки
- IoT приложений
- Чат-ботов
- Потоковой обработки

❌ **НЕ подходит для:**

- Batch обработки
- Планируемых задач
- Последовательных процессов

### Пример: Контент-платформа

```
СОБЫТИЕ 1: Пользователь загрузил видео
   ↓
→ Agent 1: Проверить на вирусы ┐
→ Agent 2: Создать превью      ├─ Параллельно!
→ Agent 3: Извлечь аудио       │
→ Agent 4: Сжать видео         ┘

СОБЫТИЕ 2: Превью создано
   ↓
→ Agent 5: Обновить базу данных
→ Agent 6: Уведомить пользователя

СОБЫТИЕ 3: Модератор одобрил
   ↓
→ Agent 7: Опубликовать
→ Agent 8: Отправить в рекомендации
→ Agent 9: Уведомить подписчиков

СОБЫТИЕ 4: 1000 просмотров
   ↓
→ Agent 10: Наградить автора баллами
→ Agent 11: Показать в трендах
```

### Типы событий

**1. User Events (действия пользователя)**

```
- Загрузил файл
- Кликнул кнопку
- Отправил сообщение
- Оплатил заказ
```

**2. System Events (системные события)**

```
- Файл обработан
- Backup завершён
- Диск заполнен на 90%
- Сертификат истекает
```

**3. Time Events (временные события)**

```
- Каждый час
- В полночь
- Через 30 минут после регистрации
- Подписка истекает завтра
```

**4. External Events (внешние события)**

```
- Webhook от GitHub
- Платёж прошёл
- Email получен
- API запрос
```

### Плюсы и минусы

**Плюсы:**

- ✅ Быстрая реакция
- ✅ Гибкость и расширяемость
- ✅ Хорошая масштабируемость
- ✅ Асинхронность
- ✅ Слабая связанность агентов

**Минусы:**

- ❌ Сложно отладить
- ❌ Трудно предсказать порядок
- ❌ Может быть "событийная буря"
- ❌ Нужна система очередей

### Событийная буря

**Проблема: Каскад событий**

```
❌ Плохо:
Событие A → Событие B → Событие C → Событие D ...
(бесконечная цепочка)

Система зависла от обработки событий!
```

**Решение: Ограничение глубины**

```
✅ Хорошо:
Максимум 3 уровня каскада
После этого → в очередь на batch обработку
```

## Гибридные паттерны

### Реальные системы комбинируют паттерны!

#### Комбинация 1: Sequential + Parallel

```
Этап 1: Исследование (Sequential)
   Research → Analysis → Report
   ↓
Этап 2: Разработка (Parallel)
   Frontend ∥ Backend ∥ Database ∥ Design
   ↓
Этап 3: Интеграция (Sequential)
   Merge → Test → Fix
   ↓
Этап 4: Тестирование (Parallel)
   Unit ∥ Integration ∥ E2E ∥ Performance
   ↓
Этап 5: Релиз (Sequential)
   Stage → Production → Monitor
```

**Преимущество:** Быстро где можно, последовательно где нужно!

#### Комбинация 2: Hierarchical + Group Chat

```
CEO делегирует задачу
   ↓
Tech Leads обсуждают подход (Group Chat)
   ↓ решение принято
Разработчики выполняют параллельно
   ↓
Code review в Group Chat формате
   ↓
Merge последовательно
```

#### Комбинация 3: Event-Driven + Hierarchical

```
Событие: Новый заказ
   ↓
Order Manager (верхний уровень)
   ↓ делегирует подзадачи
Payment Agent ∥ Inventory Agent ∥ Shipping Agent
   ↓ каждый генерирует события
Событие: Оплата получена → Отправить товар
Событие: Товар отправлен → Уведомить клиента
```

#### Комбинация 4: Parallel + Group Chat + Sequential

**Реальный пример: Code Review процесс**

```
ЭТАП 1: Parallel Review
   Security Expert ∥ Performance Expert ∥ UX Expert
   ↓ каждый оставляет комментарии

ЭТАП 2: Group Chat
   Обсуждение конфликтующих рекомендаций
   ↓ достигнут консенсус

ЭТАП 3: Sequential Fix
   Fix security → Retest → Fix performance → Retest
   ↓

ЭТАП 4: Final Approval (Parallel)
   All experts approve ✅✅✅
```

| Ситуация               | Паттерн      | Время        | Сложность       | Стоимость     |
| ---------------------- | ------------ | ------------ | --------------- | ------------- |
| Последовательные этапы | Sequential   | 🐌 Долго     | 😊 Просто       | 💰 Дёшево     |
| Независимые задачи     | Parallel     | 🚀 Быстро    | 😐 Средне       | 💰💰 Средне   |
| Нужно обсуждение       | Group Chat   | ⏱️ Средне    | 😐 Средне       | 💰💰 Средне   |
| Большая команда        | Hierarchical | ⏱️ Средне    | 😰 Сложно       | 💰💰💰 Дорого |
| Реакция на события     | Event-Driven | ⚡ Мгновенно | 😱 Очень сложно | 💰💰 Средне   |

### Дерево решений

```
Есть зависимости между задачами?
├─ Да → Sequential
└─ Нет → Параллельно?
    ├─ Да → Parallel
    └─ Нет → Нужно обсуждение?
        ├─ Да → Group Chat
        └─ Нет → Много агентов (10+)?
            ├─ Да → Hierarchical
            └─ Нет → Реакция на события?
                ├─ Да → Event-Driven
                └─ Нет → Начни с Sequential
```

## Практические советы

### 1. Начни с простого

**Уровень новичка:**

```
Первый проект → Sequential
(самый простой и понятный)
```

**Уровень опытного:**

```
Есть опыт → Parallel или Group Chat
(когда понимаешь координацию)
```

**Уровень профи:**

```
Мастер → Гибридные паттерны
(комбинируешь для оптимальности)
```

### 2. Рисуй схемы перед реализацией

**Обязательно нарисуй:**

```
□ Каких агентов используешь
□ Как они связаны
□ Что передают друг другу
□ Где могут быть узкие места
□ План обработки ошибок
```

**Пример схемы:**

```
[User Request]
      ↓
[Validator] ────┐
      ↓         │ (если ошибка)
[Processor]     │
  ↓   ↓   ↓     │
DB  API Email   │
  ↓   ↓   ↓     │
[Aggregator]    │
      ↓         │
[Response] ←────┘
```

### 3. Тестируй на малом масштабе

**Правило постепенного роста:**

```
Неделя 1: Сначала 2 агента
          ↓ работает?
Неделя 2: Добавь до 5 агентов
          ↓ всё ок?
Неделя 3: Вся система (10+ агентов)
```

**Не делай так:**

```
❌ Сразу 20 агентов
Результат: не понятно, что сломалось
```

### 4. Измеряй результаты

**Метрики для отслеживания:**

```
⏱️ Время выполнения
├─ До оптимизации: 60 минут
└─ После: 15 минут (4x ускорение!)

❌ Количество ошибок
├─ Было: 15 ошибок на 100 задач
└─ Стало: 2 ошибки на 100 задач

✅ Качество результата
├─ Sequential: 7/10
└─ Group Chat: 9/10 (лучше!)

💰 Стоимость (токены/деньги)
├─ Parallel: $5 за задачу
└─ Sequential: $2 за задачу
```

### 5. Документируй свои паттерны

**Создай шаблон:**

```
Название паттерна: "Моя обработка контента"
Используется для: Обработка пользовательского контента
Структура: Event-Driven → Parallel → Sequential
Агенты: Validator, Scanner, Processor, Notifier
Среднее время: 30 секунд
Успешность: 98%
```

**Зачем:**

- Повторное использование
- Обучение новых людей
- Улучшение со временем

### 6. Обрабатывай ошибки на каждом уровне

**Пример обработки:**

```
Sequential паттерн:
├─ Агент А упал
│  └─ Retry 3 раза
│     └─ Всё равно не работает?
│        └─ Уведомить админа + использовать fallback
│
Parallel паттерн:
├─ Один агент упал
│  └─ Остальные продолжают
│     └─ Результат помечен как "partial"
│
Group Chat:
├─ Агент не отвечает 5 минут
│  └─ Решение без него
│     └─ Quorum из оставшихся
```

### 7. Версионируй свои паттерны

```
v1.0: Sequential (простая версия)
  ↓ работает, но медленно

v2.0: Sequential + Parallel (оптимизация)
  ↓ быстрее в 3 раза!

v3.0: Event-Driven + Parallel (финальная версия)
  ↓ масштабируется, быстро, надёжно
```

## Частые ошибки и решения

### Ошибка 1: Неправильный выбор паттерна

```
❌ Использовал Sequential для независимых задач
Потерял: 70% времени

✅ Переключился на Parallel
Результат: Ускорение в 3 раза
```

### Ошибка 2: Слишком сложно с первого раза

```
❌ Сразу Event-Driven + Hierarchical + Group Chat
Результат: Запутался, не работает

✅ Начал с Sequential
Потом добавил Parallel для узких мест
Результат: Работает и понятно
```

### Ошибка 3: Нет обработки ошибок

```
❌ Один агент упал → вся система встала

✅ Добавил:
- Retry логику
- Fallback агенты
- Graceful degradation
```

### Ошибка 4: Не измерял результаты

```
❌ "Вроде работает быстрее"

✅ Замерил:
- Было: 45 секунд
- Стало: 12 секунд
- Ускорение: 3.75x
```

## Чек-лист выбора паттерна

Перед выбором паттерна ответь на вопросы:

```
□ Задачи зависят друг от друга?
  └─ Да → Sequential или Hierarchical

□ Задачи независимые?
  └─ Да → Parallel

□ Нужно обсуждение/консенсус?
  └─ Да → Group Chat

□ Много агентов (10+)?
  └─ Да → Hierarchical

□ Реакция на внешние события?
  └─ Да → Event-Driven

□ Какой приоритет:
  ├─ Скорость → Parallel/Event-Driven
  ├─ Качество → Group Chat
  ├─ Простота → Sequential
  └─ Масштаб → Hierarchical

□ Бюджет ограничен?
  └─ Да → Sequential (меньше агентов работает)

□ Есть опыт с паттернами?
  └─ Нет → Начни с Sequential
```

## 🎯 Проверка знаний

### Тестовые вопросы:

**1. Какой паттерн использовать для независимых задач?**

- A) Sequential (Последовательный)
- B) Parallel (Параллельный)
- C) Hierarchical (Иерархический)
- D) Event-Driven (Событийный)

<details>
<summary>✅ Правильный ответ</summary>
B) Parallel (Параллельный)

**Объяснение:** Если задачи не зависят друг от друга - запускай параллельно! Как в ресторане: повар варит борщ, бармен готовит кофе, официант накрывает стол - одновременно. Результат в 3 раза быстрее.

</details>

**2. В чём главная проблема паттерна Group Chat?**

- A) Медленная скорость обработки
- B) Агенты могут говорить бесконечно без решения
- C) Высокая стоимость
- D) Сложность реализации

<details>
<summary>✅ Правильный ответ</summary>
B) Агенты могут говорить бесконечно без решения

**Объяснение:** Как в реальном совещании без модератора - говорят часами, решения нет. Нужен механизм остановки: лимит раундов (10 сообщений) или детектор консенсуса.

</details>

**3. Когда использовать Sequential паттерн?**

- A) Когда все задачи независимы
- B) Когда каждый шаг зависит от предыдущего
- C) Когда нужен мозговой штурм
- D) Когда агентов больше 10

<details>
<summary>✅ Правильный ответ</summary>
B) Когда каждый шаг зависит от предыдущего

**Объяснение:** Sequential = конвейер. Нельзя класть крышу пока не построены стены. Нельзя редактировать текст пока он не написан. Один за другим.

</details>

**4. Что такое "backpressure" в Hierarchical паттерне?**

- A) Когда воркеры перегружены и не успевают
- B) Когда менеджер не раздаёт задачи
- C) Когда агенты конфликтуют
- D) Когда система падает

<details>
<summary>✅ Правильный ответ</summary>
A) Когда воркеры перегружены и не успевают

**Объяснение:** Backpressure = "обратное давление". Менеджер раздаёт задачи быстрее чем воркеры успевают. Очередь растёт, система тормозит. Решение: менеджер следит за нагрузкой.

</details>

**5. Главное преимущество Event-Driven паттерна?**

- A) Простота реализации
- B) Агенты реагируют моментально на изменения
- C) Низкая стоимость
- D) Не нужна координация

<details>
<summary>✅ Правильный ответ</summary>
B) Агенты реагируют моментально на изменения

**Объяснение:** Event-Driven = реактивность. Пришло письмо → агент обработал. Новый заказ → агент начал. Не ждут, не опрашивают - реагируют на события мгновенно.

</details>

### Задание 1: Выбор паттерна (15 минут)

**Цель:** Научиться выбирать паттерн под задачу

Для каждого сценария выбери паттерн (Sequential/Parallel/Hierarchical/Group Chat/Event-Driven):

**Критерии успеха:**

- ✅ Объяснено почему именно этот паттерн
- ✅ Названы риски выбранного паттерна

### Задание 2: Hybrid паттерн (35 минут)

**Цель:** Комбинировать паттерны для сложных задач

**Сценарий:**
Создание подкаста:

- Этап 1: 3 агента придумывают темы (Group Chat)
- Этап 2: Пишется сценарий → озвучивается → монтируется (Sequential)
- Этап 3: 4 агента публикуют в разные платформы (Parallel)

**Задача:**

1. Нарисуй схему системы (текстом/диаграммой)
2. Опиши как данные передаются между этапами
3. Посчитай время: каждый этап занимает 20 минут
4. Что будет bottleneck'ом (узким местом)?

**Критерии успеха:**

- ✅ Схема показывает все 3 этапа и агентов
- ✅ Понятен flow данных между паттернами
- ✅ Правильно посчитано время
- ✅ Найден bottleneck и предложено решение

### Задание 3: Оптимизация системы (50+ минут)

**Цель:** Превратить медленную систему в быструю

**Проблема:**
Система обрабатывает заказы:

1. Агент принимает заказ (1 мин)
2. Агент проверяет оплату (2 мин)

4. Агент отправляет на склад (1 мин)

**Текущий паттерн:** Sequential
**Проблема:** 7 минут на заказ, 100 заказов/день → очередь растёт

**Задача:**

1. Какие шаги можно распараллелить?
2. Предложи новый паттерн (может быть hybrid)
3. Посчитай новое время обработки
4. Во сколько раз быстрее?
5. Какие риски появляются?

**Критерии успеха:**

- ✅ Найдены возможности параллелизма
- ✅ Новый паттерн нарисован схемой
- ✅ Расчёты времени с обоснованием
- ✅ Учтены риски и edge cases
