# 03-ПРОДВИНУТАЯ-КОНФИГУРАЦИЯ

## 🎛️ Введение: Ваш Агент - Это Оркестр

Представьте, что вы не просто нанимаете музыканта, а создаёте целый оркестр. Каждый инструмент должен быть настроен идеально, каждый музыкант должен знать свою партию, и все должны играть в гармонии.

**Продвинутая конфигурация агентов - это искусство точной настройки**, где каждая деталь имеет значение:

- **Выбор модели** - это выбор музыкального инструмента
- **Настройка инструментов** - это определение, какие ноты можно играть
- **Версионирование** - это запись репетиций для улучшения
- **Окружения** - это выбор концертного зала

## 🎯 Глава 1: Тонкая Настройка Агентов

### Анатомия Идеального Агента

Представьте агента как швейцарский нож. У него есть основное лезвие (модель), дополнительные инструменты (tools), и инструкция по применению (system prompt).

**Базовая структура агента:**

```yaml
---
name: data-analyst
description: Анализирует данные и создаёт визуализации
model: sonnet
tools: Read, Bash, Glob, Grep
temperature: 0.3
---
Ты опытный аналитик данных, специализирующийся на Python и статистике.
```

### Параметр Temperature: Термостат Креативности

**Temperature (температура)** - это как термостат для креативности вашего агента:

- **0.0-0.3** - "Холодная голова" 🧊

  - Предсказуемые, точные ответы
  - Идеально для: математики, кода, анализа данных
  - Аналогия: _Бухгалтер, который всегда считает одинаково_

- **0.4-0.6** - "Комнатная температура" 🌡️

  - Баланс между точностью и креативностью
  - Идеально для: документации, рефакторинга, планирования
  - Аналогия: _Архитектор, который следует стандартам, но добавляет изюминку_

- **0.7-1.0** - "Горячая креативность" 🔥
  - Неожиданные, креативные решения
  - Идеально для: генерации идей, маркетинга, дизайна
  - Аналогия: _Художник, который каждый раз создаёт что-то новое_

**Пример настройки температуры:**

```yaml
---
name: creative-writer
temperature: 0.8
---
# Высокая температура для креативного письма
---
name: code-reviewer
temperature: 0.2
---
# Низкая температура для точного анализа кода
```

### Контекстное Окно: Размер Рабочего Стола

**Контекстное окно** - это как размер вашего рабочего стола:

- **Маленький стол** (4K токенов) - можно разложить одну задачу
- **Средний стол** (32K токенов) - помещается несколько файлов
- **Огромный стол** (200K токенов) - целый проект перед глазами

**Оптимизация под размер контекста:**

```yaml
---
name: quick-helper
description: Быстрые ответы на простые вопросы
model: haiku # Маленькая модель для быстрых задач
---

---
name: deep-analyst
description: Глубокий анализ всего проекта
model: opus # Большая модель с огромным контекстом
---
```

### Системный Промпт: ДНК Агента

**Системный промпт** - это ДНК вашего агента, его личность и навыки.

**Плохой промпт** (слишком общий):

```
Ты помощник программиста.
```

**Хороший промпт** (конкретный и структурированный):

```
Ты опытный Python-разработчик с 10-летним стажем.

ТВОИ ОБЯЗАННОСТИ:
1. Писать чистый, читаемый код следуя PEP 8
2. Добавлять docstrings ко всем функциям
3. Использовать type hints для всех параметров
4. Писать unit-тесты для критического кода

ТВОЙ СТИЛЬ:
- Предпочитаешь функциональное программирование
- Используешь list comprehensions вместо циклов
- Избегаешь глубокой вложенности (>3 уровней)
- Всегда обрабатываешь исключения

КОГДА СОМНЕВАЕШЬСЯ:
- Выбирай читаемость над краткостью
- Спрашивай, если требования неясны
- Предлагай альтернативные решения
```

**Аналогия:** Это как разница между "наймите программиста" и "наймите senior Python-разработчика с опытом в FastAPI, знанием архитектурных паттернов и тестирования".

## 🎨 Глава 2: Выбор Модели - Правильный Инструмент для Работы

### Семейство Моделей Claude

Представьте, что модели Claude - это семья профессионалов разного уровня:

**1. Haiku** 🍃 - Молодой стажёр

- **Скорость:** Мгновенная (⚡⚡⚡)
- **Стоимость:** Копейки
- **Контекст:** 4K токенов
- **Идеально для:**
  - Простые вопросы-ответы
  - Быстрая валидация
  - Генерация простого текста
  - Классификация данных

**Аналогия:** Стажёр, который быстро выполняет простые задачи - сделать копии, отсортировать файлы, ответить на базовые вопросы.

**2. Sonnet** 🎵 - Опытный специалист

- **Скорость:** Быстрая (⚡⚡)
- **Стоимость:** Умеренная
- **Контекст:** 200K токенов
- **Идеально для:**
  - Написание кода
  - Рефакторинг
  - Документация
  - Анализ среднего размера

**Аналогия:** Опытный разработчик, который справляется с 80% задач быстро и качественно.

**3. Opus** 🎭 - Главный эксперт

- **Скорость:** Обдуманная (⚡)
- **Стоимость:** Высокая
- **Контекст:** 200K токенов
- **Идеально для:**
  - Сложная архитектура
  - Критический код
  - Глубокий анализ
  - Креативные задачи

**Аналогия:** Главный архитектор, к которому обращаются для самых сложных и важных решений.

### Матрица Выбора Модели

**Простая формула:**

```
Сложность задачи × Важность результата = Выбор модели

Низкая × Низкая = Haiku
Средняя × Средняя = Sonnet
Высокая × Высокая = Opus
```

**Примеры решений:**

| Задача                     | Сложность | Важность | Модель | Почему                     |
| -------------------------- | --------- | -------- | ------ | -------------------------- |
| Исправить опечатку         | Низкая    | Низкая   | Haiku  | Быстро и дёшево            |
| Написать API endpoint      | Средняя   | Средняя  | Sonnet | Баланс скорости и качества |
| Спроектировать архитектуру | Высокая   | Высокая  | Opus   | Нужен лучший эксперт       |
| Генерировать тест-данные   | Низкая    | Низкая   | Haiku  | Простая генерация          |
| Ревью безопасности         | Средняя   | Высокая  | Opus   | Критично для безопасности  |

### Гибридный Подход: Команда Моделей

**Самый эффективный подход** - использовать разные модели для разных этапов:

```yaml
---
name: quick-planner
model: haiku
description: Быстро планирует задачи
---

---
name: main-developer
model: sonnet
description: Пишет основной код
---

---
name: architect-reviewer
model: opus
description: Проверяет критические решения
---
```

**Аналогия:** Как в строительстве - у вас есть разнорабочие (Haiku) для простых задач, квалифицированные мастера (Sonnet) для основной работы, и главный архитектор (Opus) для проверки.

## 🛠️ Глава 3: Инструменты Доступа - Что Может Агент

### Система Инструментов (Tools)

**Инструменты** - это руки вашего агента. Без них он может только говорить, но не действовать.

**Доступные инструменты:**

```
Read    - Читать файлы
Write   - Писать файлы
Edit    - Редактировать файлы
Bash    - Выполнять команды терминала
Glob    - Искать файлы по паттернам
Grep    - Искать текст в файлах
```

### Принцип Минимальных Привилегий

**Золотое правило:** Давайте агенту только те инструменты, которые ему действительно нужны.

**Почему это важно:**

1. **Безопасность** - меньше инструментов = меньше риска
2. **Фокус** - агент не отвлекается на лишнее
3. **Предсказуемость** - ограниченные возможности = предсказуемое поведение

**Примеры правильного ограничения:**

```yaml
---
name: code-reader
description: Только читает и анализирует код
tools: Read, Glob, Grep
# НЕТ Write, Edit, Bash - только чтение!
---

---
name: test-runner
description: Запускает тесты и читает результаты
tools: Read, Bash, Grep
# Может запускать команды, но не редактировать код
---

---
name: code-writer
description: Пишет новый код
tools: Read, Write, Glob
# Может писать, но НЕ может редактировать (безопаснее)
---

---
name: senior-developer
description: Полный доступ для опытного агента
tools: Read, Write, Edit, Bash, Glob, Grep
# Полный набор для доверенного агента
---
```

**Аналогия:** Это как система доступа в офисе - стажёру не дают ключи от всех дверей, только от тех, что нужны для его работы.

### Комбинации Инструментов для Разных Ролей

**1. Аналитик (только чтение):**

```yaml
tools: Read, Grep, Glob
```

- Может искать и читать файлы
- НЕ может изменять код
- Аналогия: _Аудитор, который только проверяет_

**2. Документатор:**

```yaml
tools: Read, Write, Grep
```

- Читает код
- Пишет документацию
- Ищет примеры
- Аналогия: _Технический писатель_

**3. Тестировщик:**

```yaml
tools: Read, Bash, Grep
```

- Читает код
- Запускает тесты
- Ищет результаты
- Аналогия: _QA-инженер_

**4. Full-stack разработчик:**

```yaml
tools: Read, Write, Edit, Bash, Glob, Grep
```

- Полный набор для комплексной работы
- Аналогия: _Senior разработчик с полным доступом_

### Безопасные Паттерны Использования Bash

**Bash** - самый мощный и опасный инструмент. Используйте его осторожно!

**Безопасные команды для Bash:**

- `npm test` - запуск тестов
- `npm run build` - сборка проекта
- `git status` - проверка статуса
- `ls -la` - просмотр файлов

**ОПАСНЫЕ команды (избегайте):**

- `rm -rf` - удаление файлов
- `sudo` - команды с правами root
- Запись в системные файлы
- Сетевые команды без ограничений

**Правило безопасности:**

```yaml
---
name: safe-tester
tools: Bash
---
Ты можешь использовать Bash ТОЛЬКО для:
  - Запуска тестов (npm test, pytest)
  - Сборки проекта (npm run build)
  - Проверки статуса (git status)

НИКОГДА не используй:
  - rm (удаление файлов)
  - sudo (привилегированные команды)
  - wget/curl (скачивание)
  - chmod (изменение прав)
```

## 📦 Глава 4: Версионирование Агентов

### Почему Нужны Версии

**Версионирование агентов** - это как Git для вашей команды AI.

**Аналогия:** Представьте, что вы пишете книгу. Первый черновик - это v1.0, после правок редактора - v1.1, после полной переработки - v2.0.

**Зачем версии:**

1. **История изменений** - знаете, что работало раньше
2. **Откат** - можете вернуться к стабильной версии
3. **Эксперименты** - можете тестировать новые промпты
4. **Командная работа** - все знают, какую версию использовать

### Семантическое Версионирование

**Формат:** `MAJOR.MINOR.PATCH`

**Правила:**

- **MAJOR (1.0.0 → 2.0.0)** - кардинальные изменения

  - Новая модель (Sonnet → Opus)
  - Полная переработка промпта
  - Другой набор инструментов
  - Аналогия: _Переезд в новый офис_

- **MINOR (1.0.0 → 1.1.0)** - улучшения

  - Добавление новых навыков
  - Улучшение промпта
  - Новые примеры
  - Аналогия: _Ремонт в офисе_

- **PATCH (1.0.0 → 1.0.1)** - исправления
  - Исправление опечаток
  - Мелкие уточнения
  - Оптимизация
  - Аналогия: _Починка принтера_

### Практика Версионирования

**Структура файлов:**

```
.claude/agents/
├── code-reviewer-v1.0.md      # Стабильная версия
├── code-reviewer-v1.1.md      # Улучшенная версия
├── code-reviewer-v2.0.md      # Новое поколение
└── code-reviewer-latest.md    # Симлинк на текущую
```

**Пример версионирования:**

```yaml
---
name: code-reviewer-v1.0
version: 1.0.0
created: 2025-01-15
description: Базовый ревьюер кода
model: sonnet
---
Проверяешь код на базовые ошибки.
```

```yaml
---
name: code-reviewer-v1.1
version: 1.1.0
created: 2025-02-01
description: Улучшенный ревьюер с проверкой безопасности
model: sonnet
changelog: |
  - Добавлена проверка безопасности
  - Улучшены комментарии
  - Добавлены примеры
---

Проверяешь код на ошибки и уязвимости безопасности.

НОВОЕ В 1.1:
- Сканирование на SQL-инъекции
- Проверка XSS-уязвимостей
- Анализ небезопасных зависимостей
```

```yaml
---
name: code-reviewer-v2.0
version: 2.0.0
created: 2025-03-15
description: AI-архитектор с глубоким анализом
model: opus
changelog: |
  - Переход на модель Opus
  - Архитектурный анализ
  - Рекомендации по производительности
breaking_changes: |
  - Требует больше контекста
  - Медленнее работает
  - Выше стоимость
---
Ты опытный архитектор, анализирующий код на глубоком уровне.
```

### Changelog и Документация Изменений

**Хороший changelog** отвечает на вопросы:

- Что изменилось?
- Почему изменилось?
- Как это использовать?
- Что может сломаться?

**Шаблон changelog:**

```yaml
---
changelog: |
  ## v2.1.0 (2025-04-01)

  ### Добавлено
  - Проверка TypeScript типов
  - Анализ производительности

  - Улучшены сообщения об ошибках
  - Оптимизирован промпт (меньше токенов)

  ### Исправлено

  - Проблемы с async/await

  ### Удалено
  - Устаревшая проверка jQuery

  ### Breaking Changes
  - Теперь требуется TypeScript 5.0+
---
```

## 🌍 Глава 5: Окружения (Environments)

### Концепция Окружений

**Окружения** - это как разные сцены для вашего агента:

- **Development (разработка)** - тренировочный зал
- **Staging (тестирование)** - генеральная репетиция
- **Production (продакшн)** - настоящее выступление

**Аналогия:** Актёр тренируется в студии (dev), репетирует на сцене (staging), и выступает перед публикой (production).

### Различия Между Окружениями

**Development (разработка):**

```yaml
---
name: dev-assistant
model: haiku  # Дешёвая модель для экспериментов
temperature: 0.7  # Высокая креативность
tools: Read, Write, Edit, Bash, Glob, Grep
verbose: true  # Подробные логи
---

Ты в режиме разработки. Можешь экспериментировать!

ОСОБЕННОСТИ DEV:
- Подробно объясняй свои действия
- Предлагай альтернативные решения
- Показывай промежуточные результаты
- Не бойся ошибаться
```

**Staging (тестирование):**

```yaml
---
name: staging-assistant
model: sonnet  # Настоящая модель
temperature: 0.4  # Баланс
tools: Read, Write, Bash, Grep
verbose: true  # Всё ещё логируем
---

Ты в тестовом окружении. Работай как в продакшене, но подробно логируй.

ОСОБЕННОСТИ STAGING:
- Работай как в production
- Логируй все действия
- Проверяй результаты дважды
- Предупреждай о рисках
```

**Production (продакшн):**

```yaml
---
name: prod-assistant
model: sonnet  # Проверенная модель
temperature: 0.2  # Низкая креативность = предсказуемость
tools: Read, Grep  # Минимальные права
verbose: false  # Только результаты
---

Ты в продакшене. Будь осторожен и предсказуем.

ОСОБЕННОСТИ PRODUCTION:
- Только проверенные действия
- Минимальные логи
- Максимальная стабильность
- В случае сомнений - спрашивай
```

### Конфигурация Через Файлы Окружения

**Структура:**

```
.claude/
├── config/
│   ├── development.json
│   ├── staging.json
│   └── production.json
└── agents/
    └── developer.md
```

**development.json:**

```json
{
  "environment": "development",
  "defaultModel": "haiku",
  "defaultTemperature": 0.7,
  "verbose": true,
  "safety": {
    "allowBash": true,
    "allowWrite": true,
    "allowEdit": true
  },
  "limits": {
    "maxTokens": 100000,
    "timeout": 60
  }
}
```

**staging.json:**

```json
{
  "environment": "staging",
  "defaultModel": "sonnet",
  "defaultTemperature": 0.4,
  "verbose": true,
  "safety": {
    "allowBash": true,
    "allowWrite": true,
    "allowEdit": true,
    "requireConfirmation": ["rm", "delete", "drop"]
  },
  "limits": {
    "maxTokens": 200000,
    "timeout": 120
  }
}
```

**production.json:**

```json
{
  "environment": "production",
  "defaultModel": "sonnet",
  "defaultTemperature": 0.2,
  "verbose": false,
  "safety": {
    "allowBash": false,
    "allowWrite": false,
    "allowEdit": false,
    "readOnly": true
  },
  "limits": {
    "maxTokens": 200000,
    "timeout": 300
  },
  "monitoring": {
    "logAllActions": true,
    "alertOnErrors": true
  }
}
```

### Переключение Между Окружениями

**Простой способ - через переменную окружения:**

```bash
# Development
export CLAUDE_ENV=development

# Staging
export CLAUDE_ENV=staging

# Production
export CLAUDE_ENV=production
```

**Аналогия:** Как переключение передач в автомобиле - разные режимы для разных условий.

### Безопасность в Разных Окружениях

**Development (можно всё):**

- Эксперименты разрешены ✅
- Ошибки - это обучение ✅
- Полный доступ к инструментам ✅
- Подробное логирование ✅

**Staging (осторожно):**

- Реалистичные условия ⚠️
- Проверка всех действий ⚠️
- Подтверждение опасных команд ⚠️
- Мониторинг производительности ⚠️

**Production (только проверенное):**

- Нулевая толерантность к ошибкам ❌
- Минимальные права доступа ❌
- Только чтение (часто) ❌
- Строгий мониторинг ❌

## 🎓 Глава 6: Продвинутые Паттерны Конфигурации

### Наследование Конфигураций

**Концепция:** Базовый агент + специализация

```yaml
---
name: base-developer
model: sonnet
temperature: 0.3
tools: Read, Write, Grep
---
Ты базовый разработчик.
```

```yaml
---
name: python-developer
inherits: base-developer
tools: Read, Write, Bash, Grep
---

Ты Python-разработчик, наследующий навыки базового разработчика.

ДОПОЛНИТЕЛЬНО:
- Специализация на Python
- Знание pytest
- PEP 8 стандарты
```

**Аналогия:** Как классы в программировании - базовый класс с общей функциональностью, и специализированные классы с дополнениями.

### Профили для Разных Проектов

**Один агент, разные настройки для разных проектов:**

```yaml
---
name: project-assistant
profiles:
  - name: frontend-project
    tools: Read, Write, Grep
    focus: React, TypeScript, CSS

  - name: backend-project
    tools: Read, Write, Bash, Grep
    focus: Python, FastAPI, PostgreSQL

  - name: mobile-project
    tools: Read, Write, Bash
    focus: React Native, iOS, Android
---
Адаптируешься под проект, выбирая соответствующий профиль.
```

### Условная Конфигурация

**Динамическая настройка в зависимости от условий:**

```yaml
---
name: adaptive-assistant
conditions:
  - if: fileType == "test"
    then:
      temperature: 0.2
      tools: [Read, Bash, Grep]

  - if: fileType == "documentation"
    then:
      temperature: 0.6
      tools: [Read, Write]

  - if: fileType == "code"
    then:
      temperature: 0.3
      tools: [Read, Write, Edit]
---
Изменяешь поведение в зависимости от типа файла.
```

**Аналогия:** Как хамелеон меняет цвет в зависимости от окружения.

### Композиция Агентов

**Создание сложного агента из простых:**

```yaml
---
name: full-stack-developer
compose:
  - agent: python-backend
    weight: 0.4
  - agent: react-frontend
    weight: 0.4
  - agent: devops-engineer
    weight: 0.2
---
Ты комбинация трёх специалистов с разными весами.
```

**Аналогия:** Как коктейль - смешиваете разные ингредиенты в определённых пропорциях для идеального вкуса.

## 🔧 Глава 7: Оптимизация и Мониторинг

### Метрики Производительности

**Что отслеживать:**

1. **Скорость ответа**

   - Среднее время выполнения
   - Время до первого токена
   - Общее время задачи

2. **Качество результата**

   - Успешность выполнения
   - Количество правок
   - Удовлетворённость результатом

3. **Стоимость**
   - Токены на задачу
   - Стоимость на день/неделю/месяц
   - ROI (возврат инвестиций)

**Пример конфига с метриками:**

```yaml
---
name: monitored-agent
monitoring:
  trackPerformance: true
  trackCosts: true
  trackQuality: true
  alertOnSlowness: 30s
  alertOnHighCost: 1000 tokens
---
```

### A/B Тестирование Агентов

**Сравнение двух версий:**

```yaml
---
name: code-reviewer-a
version: experiment-low-temp
temperature: 0.1
---

---
name: code-reviewer-b
version: experiment-high-temp
temperature: 0.5
---
```

**Метрики для сравнения:**

- Какая версия находит больше ошибок?
- Какая версия даёт лучшие рекомендации?
- Какая версия быстрее?
- Какая версия дешевле?

**Аналогия:** Как A/B тестирование в маркетинге - показываете две версии и смотрите, какая работает лучше.

### Оптимизация Промптов

**Итеративное улучшение:**

1. **Базовый промпт** (v1.0)

   ```
   Проверь код на ошибки.
   ```

2. **Улучшенный промпт** (v1.1)

   ```
   Проверь код на:
   - Синтаксические ошибки
   - Логические ошибки
   - Проблемы производительности
   ```

3. **Оптимизированный промпт** (v1.2)

   ```
   Анализируй код по чек-листу:
   1. Синтаксис и стиль
   2. Логика и корректность
   3. Производительность
   4. Безопасность
   5. Тестируемость

   Для каждого пункта дай оценку 1-5 и рекомендации.
   ```

**Правила оптимизации:**

- Делайте промпт конкретнее
- Добавляйте структуру (чек-листы, шаги)
- Давайте примеры
- Убирайте лишнее

### Кеширование и Переиспользование

**Кеширование промптов** - Claude автоматически кеширует части системного промпта.

**Как использовать:**

```yaml
---
name: efficient-agent
system_prompt: |
  # Эта часть будет закеширована
  Ты опытный разработчик с навыками:
  - Python, JavaScript, TypeScript
  - React, FastAPI, PostgreSQL
  - Docker, Kubernetes, CI/CD

  Твои принципы:
  1. Чистый код
  2. Тестируемость
  3. Документация
  4. Производительность

  # А эта часть - динамическая
  Текущая задача: {{task}}
  Контекст: {{context}}
---
```

**Экономия:**

- Кешированные токены стоят в 10 раз дешевле
- Быстрее загрузка контекста
- Меньше задержка

**Аналогия:** Как заучивание базовых знаний наизусть - не нужно каждый раз читать учебник заново.

## 🎯 Проверка знаний

### Тестовые вопросы:

**1. Что означает temperature = 0.1 для агента?**

- A) Агент будет очень креативным и непредсказуемым
- B) Агент будет строгим и предсказуемым
- C) Агент будет работать медленнее
- D) Агент будет дешевле

<details>
<summary>✅ Правильный ответ</summary>
B) Агент будет строгим и предсказуемым

**Объяснение:** Temperature - это "креативность". 0 = робот, 1 = художник. Для кода, фактов, расчётов ставь 0.1-0.3. Для копирайтинга, идей - 0.7-0.9.

</details>

**2. Зачем нужен retry с exponential backoff?**

- A) Чтобы агент работал быстрее
- B) Чтобы не перегружать API при ошибках
- C) Чтобы снизить стоимость
- D) Чтобы увеличить креативность

<details>
<summary>✅ Правильный ответ</summary>
B) Чтобы не перегружать API при ошибках

**Объяснение:** Exponential backoff = умные повторы. Ошибка → жди 1 сек. Опять ошибка → жди 2 сек. Ещё ошибка → жди 4 сек. Даёшь API время восстановиться.

</details>

**3. Что такое rate limiting?**

- A) Ограничение количества запросов в секунду
- B) Ограничение размера промпта
- C) Ограничение времени работы
- D) Ограничение стоимости

<details>
<summary>✅ Правильный ответ</summary>
A) Ограничение количества запросов в секунду

**Объяснение:** Rate limiting = "не спамь API". OpenAI разрешает 60 запросов/минуту. Превысил → ban на 1 минуту. Нужно ставить очередь и throttling.

</details>

**4. Зачем нужен timeout для агента?**

- A) Чтобы сэкономить деньги
- B) Чтобы агент не завис навсегда
- C) Чтобы ускорить работу
- D) Чтобы улучшить качество

<details>
<summary>✅ Правильный ответ</summary>
B) Чтобы агент не завис навсегда

**Объяснение:** Timeout = страховка. Агент думает 5 минут? 10 минут? Что-то не так. Ставишь timeout 60 сек → агент либо отвечает, либо говорит "не могу".

</details>

**5. Что лучше для code review агента?**

- A) temperature=0.9, max_tokens=4000
- B) temperature=0.2, max_tokens=2000
- C) temperature=0.5, max_tokens=500
- D) temperature=0, max_tokens=8000

<details>
<summary>✅ Правильный ответ</summary>
B) temperature=0.2, max_tokens=2000

**Объяснение:** Code review требует точности (low temperature) и достаточно токенов для анализа. 0.2 = строгий, 2000 токенов = хватит на файл ~500 строк.

</details>
