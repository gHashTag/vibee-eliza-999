# 🧠 Контекстное Управление

## 📖 Суть проблемы

Представьте, что вы пытаетесь рассказать другу всю историю многолетнего проекта за одну встречу. Вы начинаете с деталей первого дня, потом переходите к важным событиям второго месяца, затем к критическому моменту на третьем году... И к концу разговора ваш друг не помнит, с чего вы начинали.

**Это и есть проблема контекста для AI-агентов.**

Каждый агент имеет ограниченную "оперативную память" — так называемое **контекстное окно** (context window). Это как объём информации, который человек может удержать в голове одновременно во время разговора.

### Почему это критично?

Когда агенты работают над большими проектами:

- **Информации слишком много** — история изменений, документация, код
- **Контекст быстро переполняется** — старая информация "выпадает" из памяти
- **Важные детали теряются** — агент забывает ключевые решения
- **Эффективность падает** — приходится повторять одно и то же

## 🪟 Context Window — Окно Контекста

### Аналогия: Рабочий стол

Представьте свой физический рабочий стол. У него есть фиксированная площадь. Вы можете разложить на нём:

- 3-4 больших книги
- Или 10-15 документов А4
- Или 50+ стикеров с заметками

**Контекстное окно работает точно так же:**

```
╔════════════════════════════════════╗
║  КОНТЕКСТНОЕ ОКНО (128k токенов)  ║
╠════════════════════════════════════╣
║ ✅ Системная инструкция (5k)      ║
║ ✅ История диалога (30k)           ║
║ ✅ Текущий код (40k)               ║
║ ✅ Документация (30k)              ║
║ ✅ Результаты тестов (20k)         ║
║ ⚠️  ОСТАЛОСЬ: 3k токенов           ║
╚════════════════════════════════════╝
```

### Размеры контекстных окон

**Claude 3.5 Sonnet:** ~200,000 токенов

- Примерно 150,000 слов
- Около 500 страниц текста
- Или 75,000 строк кода

**GPT-4 Turbo:** ~128,000 токенов

- Примерно 96,000 слов
- Около 300 страниц текста
- Или 45,000 строк кода

### Что происходит при переполнении?

#### Сценарий 1: "Забывчивый профессор"

```
Агент в начале работы:
"Мы решили использовать PostgreSQL для базы данных
и Redis для кеширования."

Агент через 50,000 токенов:
"Давайте добавим MongoDB для хранения данных..."
☠️ Забыл своё же решение!
```

#### Сценарий 2: "Потерянный в лесу"

```
Этап 1: "Создаём REST API с аутентификацией"
Этап 5: "Добавим GraphQL..."
Этап 10: "Может, gRPC будет лучше?"
☠️ Потерял изначальную цель!
```

## 🤝 Context Handoff — Передача Контекста

### Аналогия: Эстафета

Представьте эстафетный бег. Один спортсмен бежит свой отрезок, затем передаёт эстафетную палочку следующему. Палочка — это **контекст**.

**Плохая передача:**

```
Агент 1 → Агент 2
"Я что-то сделал с базой данных..."
☠️ Агент 2 не понимает, ЧТО именно было сделано
```

**Хорошая передача:**

```
Агент 1 → Агент 2
📋 Резюме:
  ✅ Создана таблица users (id, name, email)
  ✅ Добавлены индексы на email
  ✅ Настроены миграции в /db/migrations/
  📁 Файлы: schema.sql, migrate.js
  🎯 Следующий шаг: Добавить таблицу sessions
```

### Три способа передачи контекста

#### 1. **Прямая передача (Direct Handoff)**

Как передача документов из рук в руки:

```
╔═══════════════╗         ╔═══════════════╗
║   Агент 1     ║ ──────→ ║   Агент 2     ║
║  (Backend)    ║  JSON   ║  (Frontend)   ║
╚═══════════════╝         ╚═══════════════╝

Передаётся:
{
  "endpoints": ["/api/users", "/api/posts"],
  "authentication": "JWT",
  "port": 3000,
  "database": "PostgreSQL"
}
```

**Когда использовать:** Последовательная работа, где каждый агент продолжает работу предыдущего.

#### 2. **Через центральную память (Shared Memory)**

Как общая библиотека, где все оставляют заметки:

```
      ╔═══════════════╗
      ║  ЦЕНТРАЛЬНАЯ  ║
      ║    ПАМЯТЬ     ║
      ╚═══════════════╝
         ↑    ↑    ↑
         │    │    │
    ┌────┘    │    └────┐
    │         │         │
 Агент 1   Агент 2   Агент 3
(читает)  (пишет)   (читает)
```

**Когда использовать:** Параллельная работа нескольких агентов над одним проектом.

#### 3. **Иерархическая передача (Hierarchical Handoff)**

Как менеджер, который делегирует задачи и получает отчёты:

```
         ╔════════════════╗
         ║ КООРДИНАТОР    ║
         ║ (Master Agent) ║
         ╚════════════════╝
              ↓  ↑  ↓  ↑
        ┌─────┴──┴──┴──┴─────┐
        ↓                     ↓
  ╔═══════════╗         ╔═══════════╗
  ║ Агент A   ║         ║ Агент B   ║
  ║ (Backend) ║         ║ (Testing) ║
  ╚═══════════╝         ╚═══════════╝
```

**Когда использовать:** Сложные задачи, требующие координации.

## 🎯 Selective Information Passing — Выборочная Передача

### Аналогия: Резюме книги

Когда вы рекомендуете другу книгу, вы не пересказываете все 300 страниц. Вы говорите:

- Основная идея
- Ключевые моменты
- Почему это важно

**Так же работает выборочная передача информации между агентами.**

### Принцип "Need to Know"

#### ❌ Плохо: Передать ВСЁ

```
Агент Frontend получает:
- Весь код backend (10,000 строк)
- Всю документацию БД
- Все логи тестирования
- Историю всех изменений
☠️ 95% этой информации бесполезно для frontend!
```

#### ✅ Хорошо: Передать НЕОБХОДИМОЕ

```
Агент Frontend получает:
- API endpoints: [список]
- Формат запросов: [примеры]
- Формат ответов: [схемы]
- Коды ошибок: [список]
✅ Всё, что нужно для работы!
```

### Техники фильтрации информации

#### 1. **По релевантности**

Представьте, что вы собираетесь в поход. Вы берёте:

- ✅ Карту местности (релевантно)
- ✅ Компас (релевантно)
- ❌ Учебник физики (не релевантно)
- ❌ Сборник кулинарных рецептов (не релевантно)

```
Агент работает над аутентификацией:
  ✅ Берёт: код авторизации, схему БД users, JWT библиотеку
  ❌ Игнорирует: код UI компонентов, стили CSS, картинки
```

#### 2. **По временной важности**

Как новостная лента:

- **Горячие новости** — последние изменения
- **Архив** — старые решения (только если нужны)

```
Последние 3 изменения: [детально]
Изменения неделю назад: [кратко]
Изменения месяц назад: [только заголовки]
Изменения год назад: [не передаём вообще]
```

#### 3. **По уровню детализации**

Как зум на карте:

- **Обзор** — общая картина
- **Средний план** — ключевые детали
- **Крупный план** — только для текущей задачи

```
ОБЗОР:
"Проект — интернет-магазин на Node.js"

СРЕДНИЙ ПЛАН:
"Backend: Express + PostgreSQL
 Frontend: React + Redux
 Деплой: Docker + AWS"

КРУПНЫЙ ПЛАН:
"Сейчас работаю над endpoints для корзины покупок:
 POST /cart/add, GET /cart/items, DELETE /cart/remove"
```

## 💾 Memory Patterns — Паттерны Памяти

### Аналогия: Три типа человеческой памяти

#### 1. **Краткосрочная память (Working Memory)**

Как записная книжка, которую вы держите в кармане во время работы.

```
Текущая задача: "Исправить баг в форме логина"
Что в памяти:
  - Код формы (100 строк)
  - Сообщение об ошибке
  - Лог последней попытки
  - План исправления

Живёт: До конца текущей задачи
```

**Использование:**

- Для активной работы прямо сейчас
- Быстрый доступ
- Маленький объём
- Очищается после завершения задачи

#### 2. **Долгосрочная память (Long-term Memory)**

Как ваш личный архив или библиотека.

```
Проектные решения:
  ✓ "Мы используем PostgreSQL, не MongoDB"
  ✓ "JWT токены с истечением 24 часа"
  ✓ "API версии 2.0, старый API deprecated"
  ✓ "Все даты в UTC"

Живёт: Всё время существования проекта
```

**Использование:**

- Для хранения ключевых решений
- Важные соглашения
- Архитектурные выборы
- История критических изменений

#### 3. **Семантическая память (Semantic Memory)**

Как ваши знания и опыт, накопленные годами.

```
Общие знания:
  - "PostgreSQL лучше для транзакционных данных"
  - "Redis хорош для кеширования"
  - "JWT не нужно хранить в БД"
  - "REST API удобнее для публичных API"

Живёт: Постоянно, переносится между проектами
```

**Использование:**

- Лучшие практики
- Паттерны решений
- Технические знания
- Опыт прошлых проектов

### Паттерны организации памяти

#### Паттерн 1: "Луковица" (Onion Pattern)

```
          ┌─────────────────────┐
          │   ТЕКУЩАЯ ЗАДАЧА    │ ← Самое важное
          │    (Ядро)           │
          └─────────────────────┘
                   ↓
          ┌─────────────────────┐
          │  НЕДАВНИЙ КОНТЕКСТ  │ ← Важно
          │   (Средний слой)    │
          └─────────────────────┘
                   ↓
          ┌─────────────────────┐
          │  ОБЩИЙ КОНТЕКСТ     │ ← Справочная информация
          │  (Внешний слой)     │
          └─────────────────────┘
```

**Принцип:** Чем ближе к ядру, тем важнее для текущей работы.

#### Паттерн 2: "Стек задач" (Task Stack)

```
┌────────────────────────────┐
│ Задача 3 (текущая)         │ ← СЕЙЧАС
├────────────────────────────┤
│ Задача 2 (приостановлена)  │ ← На паузе
├────────────────────────────┤
│ Задача 1 (приостановлена)  │ ← В ожидании
└────────────────────────────┘
```

**Принцип:** Как стопка книг — берём верхнюю, остальные ждут.

#### Паттерн 3: "Дерево знаний" (Knowledge Tree)

```
                 ПРОЕКТ
                    │
        ┌───────────┼───────────┐
        │           │           │
    BACKEND     FRONTEND      БД
        │           │           │
    ┌───┴───┐   ┌───┴───┐   ┌───┴───┐
    │   │   │   │   │   │   │   │   │
   API Auth ...  UI Form ... Schema ...
```

**Принцип:** Иерархическая организация по модулям.

## 🗜️ Context Compression — Сжатие Контекста

### Аналогия: Упаковка чемодана

Вы едете в отпуск на 2 недели. У вас есть:

- Огромный шкаф с одеждой (весь контекст)
- Маленький чемодан (контекстное окно)

**Что делать?** Сжать информацию!

### Техники сжатия

#### 1. **Суммаризация (Summarization)**

Как краткое содержание главы книги:

```
БЫЛО (5000 токенов):
[Полный код файла user-service.js: 200 строк]
[Полная история изменений: 50 коммитов]
[Полные результаты тестов: 100 тестов]

СТАЛО (500 токенов):
UserService:
  ✓ Создание пользователя
  ✓ Обновление профиля
  ✓ Удаление аккаунта
  ✓ Все тесты пройдены ✅
  📍 Последнее изменение: добавлена валидация email
```

#### 2. **Удаление дубликатов (Deduplication)**

Как убрать одинаковые фотографии:

```
БЫЛО:
Агент 1: "Используем PostgreSQL"
Агент 2: "Используем PostgreSQL"
Агент 3: "Используем PostgreSQL"
☠️ 3 раза одно и то же!

СТАЛО:
Общее решение: "Используем PostgreSQL"
✅ Сказано один раз
```

#### 3. **Извлечение ключевой информации (Key Information Extraction)**

Как выделение маркером в учебнике:

```
БЫЛО (1000 токенов):
"После долгих обсуждений команда пришла к выводу, что
для нашего проекта, учитывая специфику задач и нагрузку,
наиболее подходящим решением будет использование
PostgreSQL как основной базы данных..."

СТАЛО (50 токенов):
"База данных: PostgreSQL"
✅ Суть сохранена, 95% слов выброшено
```

#### 4. **Структурированное хранение**

Вместо текста — структурированные данные:

```
БЫЛО (JSON-текст, 300 токенов):
"API endpoints включают users endpoint по пути
/api/v2/users с методом GET, posts endpoint..."

СТАЛО (Структура, 100 токенов):
{
  "api": {
    "version": "v2",
    "endpoints": {
      "users": {"path": "/api/v2/users", "method": "GET"},
      "posts": {"path": "/api/v2/posts", "method": "GET"}
    }
  }
}
✅ Компактнее и точнее
```

### Стратегия "Умного сжатия"

#### Уровень 1: Активная работа (0% сжатие)

```
Текущий файл: ПОЛНЫЙ код (без сжатия)
```

#### Уровень 2: Недавний контекст (30% сжатие)

```
Связанные файлы: Только ключевые функции
```

#### Уровень 3: Общий контекст (70% сжатие)

```
Весь проект: Краткое резюме каждого модуля
```

#### Уровень 4: История (90% сжатие)

```
Прошлые решения: Только критические факты
```

## 🎭 Практические сценарии

### Сценарий 1: "Большой проект"

**Проблема:**
Проект состоит из 100 файлов, но контекст вмещает только 20.

**Решение:**

```
1. ТЕКУЩАЯ ЗАДАЧА (детально):
   - Файл, над которым работаем
   - Связанные тесты
   - Зависимости

2. МОДУЛЬ (сжато):
   - Краткое описание каждого файла модуля

3. ПРОЕКТ (ультра-сжато):
   - Список всех модулей
   - Ключевые технологии
   - Архитектурные решения
```

### Сценарий 2: "Передача между агентами"

**Проблема:**
Агент Backend закончил работу, нужно передать контекст агенту Frontend.

**Решение:**

```
╔═══════════════════════════════════════╗
║  ПЕРЕДАВАЕМЫЙ КОНТЕКСТ                ║
╠═══════════════════════════════════════╣
║ 🎯 ГЛАВНОЕ (что сделано):             ║
║   - REST API готов                    ║
║   - Эндпоинты: /api/users, /api/posts ║
║                                        ║
║ 📋 ДЕТАЛИ (что нужно знать):          ║
║   - Аутентификация: JWT               ║
║   - Формат ответов: JSON              ║
║   - Порт: 3000                        ║
║                                        ║
║ 🔗 ССЫЛКИ (где найти больше):         ║
║   - API docs: /docs/api.md            ║
║   - Примеры: /examples/requests.json  ║
║                                        ║
║ ⚠️  ВАЖНО (частые ошибки):            ║
║   - Добавлять Bearer token в headers  ║
║   - Даты в формате ISO 8601           ║
╚═══════════════════════════════════════╝
```

### Сценарий 3: "Длительная работа"

**Проблема:**
Агент работает 2 часа над задачей, контекст переполняется каждые 20 минут.

**Решение: Точки сохранения (Checkpoints)**

```
┌─────────────────┐
│  СТАРТ ЗАДАЧИ   │
└────────┬────────┘
         ↓
┌─────────────────┐
│  Работа 20 мин  │
└────────┬────────┘
         ↓
┌─────────────────┐
│  CHECKPOINT 1   │ ← Сохранить прогресс
│  Сжать контекст │
└────────┬────────┘
         ↓
┌─────────────────┐
│  Работа 20 мин  │
└────────┬────────┘
         ↓
┌─────────────────┐
│  CHECKPOINT 2   │ ← Сохранить прогресс
│  Сжать контекст │
└────────┬────────┘
         ↓
       [...]
```

**Что сохраняется на checkpoint:**

- ✅ Что было сделано
- ✅ Что осталось сделать
- ✅ Важные решения
- ✅ Известные проблемы

## 🧩 Паттерны взаимодействия

### Паттерн: "Мастер и Рабочие"

```
          МАСТЕР-АГЕНТ
      (Держит общую картину)
                │
        ┌───────┼───────┐
        ↓       ↓       ↓
    РАБОЧИЙ РАБОЧИЙ РАБОЧИЙ
     АГЕНТ   АГЕНТ   АГЕНТ
   (Детали) (Детали) (Детали)
```

**Как работает:**

- Мастер знает ВСЁ на высоком уровне
- Рабочие знают ДЕТАЛИ своей части
- Мастер координирует, рабочие выполняют

**Контекст:**

- Мастер: Общая архитектура (сжато)
- Рабочий: Детали своей задачи (полностью)

### Паттерн: "Конвейер"

```
Агент 1  →  Агент 2  →  Агент 3  →  Агент 4
(Дизайн)   (Код)      (Тесты)     (Деплой)
```

**Передача контекста:**

```
Агент 1 → Агент 2:
  "Дизайн: [файлы]
   API спека: [схемы]"

Агент 2 → Агент 3:
  "Код: [ссылки на файлы]
   Что тестировать: [чеклист]"

Агент 3 → Агент 4:
  "Тесты: ✅ Все прошли
   Готово к деплою: [список файлов]"
```

**Принцип:** Каждый агент передаёт только то, что нужно следующему.

### Паттерн: "Роевой интеллект"

```
    ┌─────────────────┐
    │ ОБЩАЯ ПАМЯТЬ    │
    │  (Shared State) │
    └─────────────────┘
      ↑  ↑  ↑  ↑  ↑
      │  │  │  │  │
     А1 А2 А3 А4 А5
```

**Как работает:**

- Все агенты читают из общей памяти
- Каждый пишет результаты своей работы
- Самоорганизация без центрального управления

**Контекст:**

- Общая память: Ключевые факты (структурировано)
- Каждый агент: Своя задача + общая память

## 🎯 Золотые правила контекстного управления

### Правило 1: "Передавай СУТЬ, а не ВСЁ"

```
❌ Плохо:
```

## 🎓 Вывод

**Контекстное управление — это искусство:**

1. **Знать ЧТО важно** — отделять сигнал от шума
2. **Знать КОГДА важно** — время и релевантность
3. **Знать КАК передать** — формат и структура
4. **Знать СКОЛЬКО передать** — баланс детализации

**Помните:**

- Агент — не человек, у него есть строгий лимит памяти
- Хороший контекст — это не ВСЯ информация, а НУЖНАЯ информация
- Сжатие контекста — не потеря данных, а фокусировка на важном
- Передача контекста — не дамп данных, а осмысленная коммуникация

**Главный принцип:**

> "Передавай другим агентам то, что хотел бы получить сам,
> если бы начинал работу с нуля по этой задаче."

## 🎯 Проверка знаний

### Тестовые вопросы:

**1. Что такое context window?**

- A) Время работы агента
- B) Максимальное количество токенов которое агент может обработать
- C) Размер экрана для отображения
- D) Скорость обработки запросов

<details>
<summary>✅ Правильный ответ</summary>
B) Максимальное количество токенов которое агент может обработать

**Объяснение:** Context window - это "память" агента. GPT-4: 128k токенов (~100 страниц). Claude 3: 200k токенов (~150 страниц). Больше window = больше помнит, но дороже.

</details>

**2. Зачем нужно сжимать контекст?**

- A) Чтобы ускорить работу
- B) Чтобы сэкономить деньги и не превысить context window
- C) Чтобы улучшить качество
- D) Чтобы агент работал стабильнее

<details>
<summary>✅ Правильный ответ</summary>
B) Чтобы сэкономить деньги и не превысить context window

**Объяснение:** Каждый токен стоит денег! История из 10 сообщений = 5000 токенов. Сжал до summary = 500 токенов. Экономия 10x. Плюс не выходишь за лимит.

</details>

**3. Что такое "selective information passing"?**

- A) Передача ВСЕХ данных между агентами
- B) Передача ТОЛЬКО нужной информации
- C) Случайная передача данных
- D) Шифрование данных

<details>
<summary>✅ Правильный ответ</summary>
B) Передача ТОЛЬКО нужной информации

**Объяснение:** Не гони весь context! Агент 1 → Агент 2: передай только выводы, а не весь анализ. Как в офисе: менеджеру не нужны технические детали, только результат.

</details>

**4. Когда использовать context handoff?**

- A) Всегда
- B) Когда агент 1 закончил работу и агент 2 продолжает
- C) Никогда
- D) Только при ошибках

<details>
<summary>✅ Правильный ответ</summary>
B) Когда агент 1 закончил работу и агент 2 продолжает

**Объяснение:** Handoff = эстафета. Агент 1 написал код → передаёт агенту 2 (тестировщику). Агент 2 не нужна ВСЯ история - только код и требования.

</details>

**5. Главная проблема при длинных диалогах?**

- A) Агент забывает начало разговора
- B) Агент работает медленно
- C) Стоимость растёт с каждым сообщением
- D) Все вышеперечисленное

<details>
<summary>✅ Правильный ответ</summary>
D) Все вышеперечисленное

**Объяснение:** Длинный контекст = 3 проблемы: 1) Агент теряет фокус на старых сообщениях, 2) Latency растёт (дольше думает), 3) Каждое сообщение дороже (отправляешь весь history).

</details>

### Задание 2: Context handoff (30 минут)

**Цель:** Спроектировать передачу контекста между агентами

**Сценарий:**
Создание лендинга:

1. **Agent 1 (Analyst):** Анализирует конкурентов (output: 5000 токенов)
2. **Agent 2 (Designer):** Создаёт дизайн
3. **Agent 3 (Copywriter):** Пишет тексты
4. **Agent 4 (Developer):** Код

**Задача для каждого handoff:**

- Agent 1 → Agent 2: что передать?
- Agent 2 → Agent 3: что передать?
- Agent 3 → Agent 4: что передать?

**Нарисуй схему:**

```
[Agent 1: 5000 tokens] → [сжато до ? tokens] → [Agent 2]
[Agent 2: ? tokens] → [сжато до ? tokens] → [Agent 3]
```

**Критерии успеха:**

- ✅ Для каждого handoff определён минимальный контекст
- ✅ Схема показывает сжатие на каждом шаге
- ✅ Посчитана экономия токенов
- ✅ Убедись что ничего важного не потеряно

### Задание 3: Long-term memory (45+ минут)

**Цель:** Реализовать систему для диалогов на 1000+ сообщений

**Проблема:**
Чат-бот консультант работает месяцами с одним клиентом. История растёт до 50,000 токенов. Context window = 128k, но стоимость огромная.

**Задача:**
Спроектируй систему управления контекстом:

1. **Compression strategy:**

   - Что сжимать?
   - Как часто?
   - Какой алгоритм?

2. **Storage:**

   - Где хранить старые сообщения?
   - Как быстро искать нужное?
   - Что хранить в long-term memory?

3. **Retrieval:**

   - Как понять что нужно достать из истории?
   - Сколько контекста подгружать?
   - Как ранжировать по релевантности?

4. **Metrics:**
   - Посчитай cost сейчас vs после оптимизации
   - Посчитай latency (время ответа)
   - Оцени риск потери важной информации

**Критерии успеха:**

- ✅ Детальная стратегия compression
- ✅ Архитектура storage с технологиями
- ✅ Алгоритм retrieval с примерами
- ✅ Расчёты cost/latency до и после
